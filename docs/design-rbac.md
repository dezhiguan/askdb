## 一、背景与目标

askdb 已上线 5 个内置角色、10 名内置人员、8 个功能页。但**角色目前只对"查数"这一条路径生效，且只有两个维度（可见表、行上限）**；权限页上展示的其余维度与策略多数没有后端执行。

本设计的目标：把"页面上宣称的权限"与"运行时真正执行的权限"对齐，并在**不新增角色、不调整人员归属**的前提下，为现有每一项功能明确责任边界。

### 三条设计原则

1. **每一条权限都要对应一个具体的执行动作**。落不到护栏或接口拦截上的条目，宁可在页面上标注"未接入"，也不放进矩阵充数 —— 这是 `identity.py` 里"角色固定不开放自定义"那段注释已经确立的原则，本设计沿用。
2. **只能收窄，不能放宽**。沿用 `identity.policy_for` / `narrow` 的既有语义：配置与内置默认取交集，角色叠加取并集，但每个策略本身都是实例白名单的子集。
3. **提出与放行分属两人**。改数据边界的不自己放行这次变更。**所有审批闸门收敛到系统管理员**（V1.1 决定）。

   > **V1.4 修订：** 这一条原来还有一层"管人的不看数据"，并由此得到一条结构性保证 —— 系统管理员的内置策略是 `Policy(tables=frozenset(), max_rows=0)`，永远不可能是查询的发起人，自批在结构上不可能发生。2026-09-06 产品决定所有角色可见面一致、系统管理员也能查数，**这条结构性保证已经不存在**，改由 `approvals.decide` 里的显式判定（发起人 == 审批人则 403）顶上。一条隐式保证换成了一条显式判定：后者可以被绕过、被误删、被重构掉，前者不会。改审批链路前先读那一处，并确认它仍有测试覆盖。

   代价要讲清楚：审批人必须看到问题原文与最终 SQL 才能判断该不该放行，所以「系统管理员不看查询内容」这条要在**审批场景内**放宽（见脚注 12）。放宽的是可见性，不是数据权限 —— 审批通过后任务以**发起人的角色**恢复执行，审批人拿不到任何结果集。

## 二、现状盘点：宣称 vs. 真实

### 2.1 真正在跑的授权面

| 机制 | 实现位置 | 生效范围 |
|---|---|---|
| 表白名单收窄 `tables` | `identity.Policy` → `narrow()` → `cfg.tables` | 护栏 R-03、Schema 召回、口径过滤，全链路 |
| 行上限收窄 `max_rows` | 同上 → `cfg.max_rows` | 执行器 R-13 |
| 系统角色零数据权 | `DEFAULT_POLICIES["SYS_ADMIN"]` | 内置默认，配置改不动 |
| 生产只读（P01） | 护栏层强制只读事务 + R-01/R-02 | 所有连接，与角色无关 |
| 登录门 | `_require_login` —— 无中间件、无全局 `Depends` | **仅** `/api/ask`、`/api/sql` 两处显式调用；`/api/tasks` 自带一份等价判断。其余接口不设门（D-3 实测） |

### 2.2 页面上宣称、后端没有的

| 展示项 | 页面来源 | 真实状态 |
|---|---|---|
| 环境范围 `PROD-RO` / `STAGING` / `DEV + STAGING` | `role.scope`，真值字段 | **纯展示字符串，无任何执行判定** |
| 数据期限 `90 DAYS` 等 | `PermissionsPage.ROLE_LIMITS` 硬编码 | 无后端字段 |
| 敏感字段 `MASKED` | 同上 | 全仓无列级脱敏实现 |
| 导出权限 `AGG ONLY` | 同上 | 无导出功能 |
| P03 个人信息默认脱敏 | `POLICY_RULES` 前端 state | 无存储、无执行 |
| P07 高成本查询二次确认 | 同上 | 无审批流 |
| P11 结果禁止用于模型训练 | 同上 | 无留存策略字段 |

### 2.3 必须先处理的六个缺陷

**D-1（高）· 环境范围形同虚设。** `_cfg_for(source)` 只按 id 取源，取完才按角色收窄表与行数。角色对"能连哪个库"没有任何约束 —— 只要数据源列表里有生产只读镜像，测试角色照样能选中并查询。`sources.py` 里 `Source.env` 字段的注释写得很直白 ——「环境标签，仅用于界面区分，**不参与鉴权**」。角色详情第一格 `STAGING` 因此是**页面上唯一一个看起来是真值、实际不成立的字段**，比纯占位更有误导性。

附带一个规模问题：`env` 的取值只有 `test` 与 `prod_ro` 两种（`build()` 里非法值一律回退 `test`），而角色 scope 区分了 `DEV + STAGING` 与 `STAGING` 两档。**枚举撑不起角色已经宣称的粒度**，需一并扩展。

**D-2（高，动手时已被关闭）· 数据源写接口只有部署级开关，没有请求方身份判定，且是提权路径。** `POST /api/sources`、`PUT /api/sources/{id}/tables`、`DELETE /api/sources/{id}` 走 `_sources_gate()`，它校验的是实例开关 `datasources.allow_runtime_add` 与频率限制 —— **是「这个实例允不允许」，不是「这个人允不允许」**；函数签名里连 `request: Request` 都没有，拿不到调用方身份。`config/askdb.yaml` 当前该开关为 `true`，即任何能打开页面的人都能调。其中改白名单直接决定 `cfg.tables` —— **一次无身份判定的白名单写入，等于给所有角色同时放宽可见表**，绕开了「只能收窄」这条不变量的全部保护。

**补记（2026-09-06）**：着手实现时发现 `server.py` 已新增写入中间件 `_gate_writes`，对全部 POST/PUT/PATCH/DELETE 强制要求会话或管理员令牌，D-2 因此在本轮动手前即已关闭。本轮补的是它之上的一层：**按角色**判定谁能写，而不只是「登录了就能写」。

**D-3（高，实测确认）· 未登录拦截只覆盖了查询路径，治理面没拦。**

2026-09-05 对本机实例（`127.0.0.1:8011`，`auth.required: true`）不带任何会话 cookie 逐个打接口，实测结果：

| 接口 | 无会话时 |
|---|---|
| `/api/tasks` | **401** —— 拦住了 |
| `/api/audit` | **200** —— 1502 条审计流水 |
| `/api/audit/stats` | **200** |
| `/api/identity/members` | **200** —— 返回成员名册 |
| `/api/schema` | **200** —— 8 KB 表结构 |
| `/api/sources`、`/api/eval`、`/api/quality/live` | **200** |

匿名从 `/api/audit` 拿到的单条记录含 `user`、`role`、`question` 三个字段 —— **即「谁、以什么角色、问了什么原话」**，1502 条全都可翻。

根因是 `_require_login` 靠逐接口手工调用来覆盖，全仓只挂在 `/api/ask` 与 `/api/sql` 两处（`/api/tasks` 自己写了一份等价判断）；没有中间件、没有全局 `Depends`。**审计中心保护的是「谁查了什么」，它自己不设门。**

**D-4（中）· 复放是一条按原记录权限读取的通道。** `/api/replay` 默认关闭（`observability.replay_api`）、有字段白名单与限流，这几层做得很扎实；缺的是**调用方是谁**这一层。开关一旦打开，低权限者拿到 trace_id 即可读到数据负责人查询的最终 SQL 与执行链路。

**D-5（高）· MCP 通道完全绕开角色。** `askdb/mcp_server.py` 的 `build_server(cfg)` 直接持有启动配置，`ask` / `run_sql` / `schema` 三个工具都不经过 `_scoped()`，**以实例白名单全量运行，没有角色、没有身份、没有 user 字段**。护栏与只读约束仍然生效（这条通道不能写数据），但「谁能看哪些表」这一层在这里是空的。对外接入的 Agent 因此拥有超过任何内置角色的可见范围，且审计里的 `user` 为空。

**D-6（中）· 导出不经服务端，导出权限无处施加。** 审计中心的「导出审计报告(CSV)」与执行追踪的「导出 OpenTelemetry」都是浏览器端把已拉取的数据拼字符串下载，**没有后端导出接口**。这意味着权限页宣称的 `AGG ONLY`「导出权限」维度在当前架构下没有任何可施加的位置 —— 数据一旦进了页面就已经出去了。真正的控制点在 A-01/A-03 的读取范围，不在导出动作本身。

## 四、角色权限矩阵

> **V1.4（2026-09-06）：这一节整张矩阵被一条规则取代。**
>
> 原矩阵按五个角色 × 27 个权限点分档，落地后暴露出两个问题：一是差别解释不清（为什么产品能看 90 天而测试是 180 天，没有业务依据）；二是它把登录做成了**降权** —— 产品角色登录后看到的东西比匿名还少（匿名有 `QUERY_SQL`、`AUDIT_ALL`、`INTROSPECT`，产品没有）。产品决定推倒这套分档。

### 4.1 现行模型（三条，代码里就是这三行）

| | 可见面（表 / 行上限 / 期限 / 脱敏） | 读类能力位 | 写类能力位 | 审批 |
|---|:--:|:--:|:--:|:--:|
| 未登录（`ANONYMOUS`） | 与登录用户相同 | ✅ 全部 | ✕ | ✕ |
| 其余全部 14 个角色（产品 / 开发 / 测试 / 设计 / 数据 / 运营 / 销售 / 市场 / 客服 / 财务 / 人力 / 法务合规 / 管理 / 其他） | 相同 | ✅ 全部 | ✅ 全部 | ✕ |
| 系统管理员 | 相同 | ✅ 全部 | ✅ 全部 | ✅ **唯一** |

1. **所有角色的可见面完全相同**，包括匿名。`DEFAULT_POLICIES` 是空字典，仓库里没有任何一份配置写 `role_policies`。
2. **唯一的角色差别是 `APPROVE`**，只有系统管理员有。
3. **未登录可读不可写。** 这一条**不由角色表达**：真正的边界是 `server._gate_writes` 中间件，按 HTTP 方法拦下所有未登录的 `POST/PUT/PATCH/DELETE`，新增接口默认落在安全那边。能力位里把写类从匿名身上摘掉，只是让页面能提前置灰（前端 `writeGuard`）。

### 4.2 脱敏与数据期限

- **脱敏**：个人信息列在执行器返回前无条件脱敏，**没有任何角色能关掉**。原先 `Policy.unmask` 这一位已删除（原来给开发与数据负责人）。
- **数据期限**：内置默认不设窗口，对所有角色都是"不限"。护栏 R-19 的机制保留并仍有测试覆盖，部署方可在 `role_policies` 里手工收紧 —— 但那是一个会让角色之间重新出现差别的决定。

### 4.3 保留下来的收窄机制

`identity.policy_for` / `narrow` / `combine` 全部保留，「只能收窄不能放宽」这条不变量仍由 `narrow()` 保证并有测试覆盖。删的是**取值**，不是机制：配置写什么都不可能放宽，这一点比"现在没人配"更重要。

## 五、人员到权限的落地对照

现有 10 名内置人员，归属不变。

> **V1.5（2026-09-08）补记：** 名册规模已不是 10 人 —— 身份库里另有一万条角色成员记录（`created_by = 'roster-v1'`，由 `seed_identity_roster.py` 生成）。它们**只回答「谁属于哪个角色」，不带登录能力**（`auth_user_id` 全为空），因此下表按角色归纳的结论对这一万人同样成立：可见面完全相同，写位靠登录，审批只有系统管理员。角色分布见该脚本的 `DEPARTMENTS`，那里是唯一事实来源。

### 两个必须先确认的问题

**人员核对：** 权限页显示系统管理员 2 人，而 `config/askdb.yaml` 的 `auth.accounts` 里只有徐婷一人。差额来自身份库 `askdb_role_members` 中一条手工登记、`auth_user_id` 为空（未绑定网关用户）的记录。**权限最高的角色里存在一个来路需要核对的成员**，上线前须查明并处置。

**单点风险（V1.1 后位置变了，V1.4 后更重）：** 审批不再压在何静身上，而是全部压在系统管理员上。V1.4 之后这个角色还多了数据可见权与成员增删权 —— 同一个未经核实的账号现在既能查数、又能放行审批、又能改成员名单。权限页显示该角色 2 人，但其中一人正是上面那条来路待核的记录 —— **换句话说，现在有一个身份未经核实的账号持有全部审批权**。O-1 因此从「上线前须查明」升级为「阻塞项」。

核实完成后若确认系统管理员实为徐婷一人，需要一名备份审批人。可用 RBAC 的加法语义（`identity.combine` 已支持多角色叠加）给某位成员叠加 `SYS_ADMIN` —— **不新增角色、不调整人员**，只在成员表里多一条登记。备份人选不能是何静：她是数据源变更的提出方，兼任放行方会让「提出与放行分属两人」失效。

## 六、落地路径

> **实现状态（2026-09-06）**：四个阶段均已落地在分支 `feat/authz-enforcement`。
> 下面保留原计划文字，并在相关处补「实际落地」说明差异 ——
> 计划与实现不一致而不写下来，正是本文档第一节要消灭的那种漂移。

### 阶段一 · 鉴权兜底（2026-09-08 ~ 2026-09-19）

目标：把裸奔的接口关上。这一阶段不引入任何新权限维度，只让"已有的角色"覆盖到"已有的接口"。

1. 登录判据从逐接口调用改为默认要求，白名单显式列出：`/api/health`、`/api/auth/*`、`/api/identity/roles`、静态资源。当前 `_require_login` 只挂在 4 个接口上，靠"记得加"来保证覆盖，接口一多必漏。
2. `/api/sources` 的三个写接口（S-03/04/05）收敛到数据负责人；`/api/introspect`、`/api/identity/members`、`/api/audit`、`/api/replay` 按矩阵设门。
3. 审计与追踪按 `user` 字段做可见范围过滤 —— 审计记录里已经有 `user` 与 `role` 两个字段，不需要新增存储。
4. 复放改为按复放者当前角色调用 `_scoped()` 重新收窄（D-4）。
5. **MCP 通道纳入角色体系（D-5）**：`build_server` 接收一个角色码（由启动参数或调用方凭据指定），内部改走 `identity.for_role(cfg, role)`，默认值取最保守的角色而非全量配置；审计记录补上调用方标识。在此之前，MCP 服务不应对内网以外开放。

**验收：** 以每个角色的账号登录，逐条走矩阵，越权项返回 403 且文案指向"当前角色无此权限"而非通用护栏措辞。

### 阶段二 · 让环境范围成立（2026-09-22 ~ 2026-10-10）

目标：消除 D-1，使 `role.scope` 从展示字符串变为执行判定。

1. `Source.env` 字段**已存在**，需要做的是两件事：把枚举从 `test` / `prod_ro` 扩为 `dev` / `test` / `prod_ro`（已有数据源回填），并**删掉「不参与鉴权」这条注释所描述的现状** —— 让它真正参与判定。
2. `Policy` 增加 `envs` 维度，语义与 `tables` 一致：收窄、取交集、多角色取并集。
3. `_cfg_for(source)` 之后增加环境归属校验；`/api/sources` 列表按环境过滤（脚注 7）。
4. 权限页四格中的"环境范围"改为读取真实生效值。

**验收：** 测试角色账号在数据源列表中看不到生产只读镜像；直接构造请求指定其 id 返回 403。

### 阶段三 · 脱敏与数据期限（2026-10-13 ~ 2026-10-31）

目标：P03 与"数据期限"落地。两者都可复用现成机制，不需要新造判定。

1. **列级脱敏**：`Policy` 增 `masked_columns`（按列名模式匹配）。落点在执行器返回前的结果处理；R-05 展开 `SELECT *` 时已经拿到了真实列名，脱敏所需的列信息现成。
2. **数据期限**：`Policy` 增 `max_age_days`，**复用 R-10 的强制谓词注入机制** —— R-10 已经在做"给 SQL 强制注入租户谓词"，时间窗口是同一类动作，注入一个时间条件即可，不需要新的护栏规则。
3. 权限页去掉 `ROLE_LIMITS` 硬编码，改读后端真值。

**验收：** 产品角色查询个人信息列返回脱敏值；查询 90 天前的数据返回空集且执行计划中可见注入的时间谓词。

> **V1.4 修订：** 脱敏落地后又收紧了一次 —— `Policy.unmask` 整位删除，脱敏在执行器里**无条件生效**，没有任何角色或配置能关掉。数据期限则相反：机制（R-19）保留，但内置默认对所有角色都是"不限"，只有部署方显式配 `role_policies` 时才生效。

**实际落地：** 规则编号取 **R-19** 而非 R-18 —— 后者已被「扇出放大」占用，占用他人编号会让审计里两类拦截混成一个码。敏感与时间标记声明在**列**上（`Column.sensitive` / `Column.time`）而不是角色上：清单分散到角色，加一张表就要改 N 处，漏一处就是一次泄露。

另有一处按既有先例的取舍：**运行时数据源上不做期限收窄**。`derive_config` 里租户隔离早就因为「一次结构扫描看不出哪一列代表租户」而一律关闭，时间列是同一个问题 ——猜错会悄悄给出错误的数据，比越权更难发现。如实关闭并标注，要收窄仍需写配置声明时间列。

### 阶段四 · 高成本查询审批闭环（2026-11-03 ~ 2026-11-21）

目标：P07 落地。

1. R-11 已在执行前用 EXPLAIN 估算扫描行数，阈值判定的输入现成。
2. 超阈值不再直接拒绝，而是把任务置为"待审批"落入任务中心 —— 任务中心已有断点续跑的执行线程模型，挂起与恢复是同一套机制。
3. **系统管理员**在待审批队列审批（V1.1）。通过则以**发起人的角色**恢复执行 —— 不是审批人的角色。
   > **V1.4 修订：** 原文接着写"也不可能是：审批人内置零表"。零表默认 2026-09-06 已撤，这条推理不再成立。发起人自己重跑这一点没变（服务端从不代执行），但"审批人的角色跑不出东西"这条附带保证没有了。
4. 审批动作独立留痕，记录审批人、时间、决定，以及**审批人查看了哪条查询的原文**。
5. 同一批次落地另外两条审批链：敏感字段按需放开（Q-06）、数据源与白名单变更（S-03/04/05）。三条链共用同一个待审批队列与同一套留痕。

**验收：** 测试角色发起一条预估扫描超阈值的查询，任务进入待审批；徐婷账号批准后任务恢复并完成，审计中同时存在发起与审批两条记录。
**实际落地：** 批准后**由发起人自己重发一次**，服务端只放行 R-11 那一道，不代为执行。这样「以发起人的角色恢复执行」自然成立，服务端不需要存任何人的凭据，也不存在审批人用自己的身份跑出别人查不到的数据这种可能。放行绑定四条（单号 + 本人 + 内容指纹 + 一次性），缺一条都不是「这个人这次这条请求」。

补充两条反向用例：何静账号对该条审批返回 403（数据负责人无放行权）；何静自己发起的超阈值查询同样进入待审批，且她本人批不了。

### 不做的部分

- **P11 结果禁止用于模型训练**：在没有导出功能、结果不落盘的当前架构下，这条已经由"结果只在任务生命周期内处理"天然成立。**不新增开关**，改为在权限页把它标注为架构约束而非可配置策略 —— 一个永远为真且拨不动的开关，比没有这个开关更容易让人误判。
- **导出权限 / AGG ONLY**：没有导出功能，这一维度暂不定义。若后续引入导出，需同步定义"聚合结果"的判定标准（是否含 GROUP BY 不足以判定，`SELECT id FROM t GROUP BY id` 仍是明细）。
- **策略开关的持久化（I-04）**：阶段一至四中，P01/P03/P07 的开关状态由配置文件承载，权限页保持只读展示。把策略做成页面可拨的开关，意味着策略变更没有评审、没有版本、没有回滚 —— 那是比"开关拨不动"更严重的问题。

## 附 · RBAC 与租户隔离是两套正交机制

本设计只讨论 RBAC。需要明确的是，它与已有的租户隔离**解决的不是同一个问题，不能互相替代**：

| | 控制什么 | 实现 | 配置 |
|---|---|---|---|
| 角色（RBAC） | **能看哪些表、哪些列** | `Policy.tables` → `cfg.tables` → R-03 | `role_policies` |
| 租户（Tenant） | **同一张表里能看哪些行** | R-10 强制注入 `org_id` 谓词 + PostgreSQL RLS 双保险 | `tenant` 段，`on_unresolved: reject` |

两者叠加才是完整边界：角色放行了 `documents` 表，租户仍然只让你看到自己组织的行。本设计新增的三个维度中，**数据时间窗口（Q-07）与租户属于同一类**（都是行级收窄、都靠谓词注入），因此阶段三复用 R-10 的机制是顺理成章的；而脱敏（Q-06）是列级，属于角色这一侧。
