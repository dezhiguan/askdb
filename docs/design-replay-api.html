1为什么要做

1.1页面正在承诺一个用不了的能力

提问结束后，结果区会显示：

trace_id  f8551ebadb0e   [复制]
原样复现整条判定链路：askdb replay f8551ebadb0e -c config/public.yaml   [复制命令]

评测页的失败样本明细里也给了同样的命令。但访问者进不了容器 —— 这条命令对页面前的人毫无意义。

这是同一类问题的第四次 此前已修过三处「界面承诺了做不到的事」：接入页的「连接数据源」实为只读回显、 askdb replay 命令一度根本不存在、评测页写着「每条失败都带 trace_id 可原样复现」却既不列 trace_id 也无入口。 它们的共性是：能力做了、文案宣称了，但把两者接起来的那一段没做。

1.2而检查点恰好是这个项目最值钱的部分之一

设计文档 §1 把核心命题定为「在模型不可靠的前提下，让整条执行链路可靠」。 检查点是这句话唯一可以被他人核验的证据 —— 它能把下面这串完整摊开：

模型第一次写了什么 → 被哪条规则拦下 → 真实错误怎么回灌 → 第二次改成了什么 → 哪一步是首个偏离步

目前这部分只有能登服务器的人看得到。§10.1 要求的「失败报告按步拆解、 标注首个偏离步」在命令行已经实现，页面上是空白。

2目标与非目标

目标

  • 页面上可查看任意一次调用的完整判定链路
  • 标注首个偏离步（§10.1）
  • 失败样本可从评测页一键跳转查看
  • 接口本身在任何实例上都不泄露数据 —— 不依赖部署方记得关开关

非目标

  • 不做「重新执行」——只读回放，不重跑任何 SQL
  • 不做跨调用检索 / 列表页（无账号体系，列表即枚举）
  • 不返回查询结果行
  • 不做检查点的保留期管理（另案）

4接口设计

4.1路由与响应

GET /api/replay?trace_id=f8551ebadb0e
情形状态码响应
正常200{ok:true, trace_id, steps:[…], first_deviation:n}
trace 不存在404{ok:false, hint:"…"}
功能未开启404与「不存在」返回完全一致 —— 见 §5.2
trace_id 格式非法422参数校验，不进入检查点库

4.2字段白名单 —— 本设计的核心决定

AskState 共 35 个字段，其中两个绝不能出接口：

字段出接口理由
rows否真实查询结果行。公开实例连的是合成库、此处无敏感数据 —— 但同一份代码会部署到连生产库的实例上，靠「记得关开关」保安全是不可接受的
schema_prompt否完整注入文本，含全部表结构与业务口径定义。体量大，且等于把白名单细节和盘托出
next / attempt / step_no是链路位置与重试计数
sql_raw / sql_final是模型产出与强制改写后 —— 这正是要展示的东西
rejected_by / error是规则编号与真实错误原文
rules_fired / rewrites是命中的规则与人类可读的改写说明
row_count / explain_rows是只给条数，不给内容
goal / converged_early是多步规划的本步目标与收敛原因
为什么用白名单而不是黑名单 黑名单要求「每次给 AskState 加字段时都记得评估要不要屏蔽」—— 这条纪律迟早会破。白名单的失败方向是漏给一个无害字段（体验问题）， 黑名单的失败方向是漏挡一个敏感字段（安全事故）。 让失败朝安全的方向发生。

4.3首个偏离步

后端计算，不交给前端 —— 判定规则应与 CLI 完全一致，两处各写一遍必然漂移：

# 第一个出现 error 或 rejected_by 的快照下标
first_deviation = next((i for i, s in enumerate(steps)
                        if s["error"] or s["rejected_by"]), None)

5安全设计

5.1三条风险

#风险缓解
高 回放内容泄露数据。状态里带着结果行与完整 schema 字段白名单（§4.2）从接口层杜绝，不依赖配置开关
中 trace_id 枚举。askdb 无账号体系，拿到 id 就能看 id 为 12 位十六进制（约 7.9×1014 空间）；接口按 [0-9a-f]{12} 严格校验；命中与未命中同为 404，不区分「不存在」与「存在但无权」；单独限流
中 检查点库被当作查询接口滥用。每次回放都要开 SQLite 并遍历历史 nginx 单开一档 30r/min；响应加 Cache-Control: no-store（内容含判定细节，不宜被中间层缓存）

5.2双开关：白名单 + 配置

两层独立生效，任一层都足以防止泄露：

# config/public.yaml
observability:
  replay_api: true     # 默认 false。连真实数据源的实例不要打开
关闭时返回 404 而不是 403 403 等于告诉探测方「这里有个功能，只是没开」。 404 与「trace 不存在」完全一致，不泄露该实例是否具备该能力。
配置replay_api理由
public.yaml（对外实例）开连合成样例库，且字段白名单已挡住结果行
askdb.yaml（本机开发）开本机自用
ragforge-prod.yaml关连真实生产库 —— 即便白名单已挡住结果行，SQL 文本本身也会暴露业务口径与表结构细节
ragforge-eval.yaml关同上

8风险与未决

等级事项处理
中检查点库无限增长。当前无保留期，WAL 已达 2.3MB 且持续增长本设计不处理，但会因此更快暴露。建议另立「检查点保留期」议题（按天清理或按容量滚动）
中SQL 文本本身即敏感信息。即便不返回结果行，生产库的 SQL 也会暴露表结构与业务口径正是生产配置默认关闭的理由。若将来要开，需要先有账号体系
低回放需打开 SQLite 并遍历历史，冷启动有延迟先观测；必要时加短 TTL 的内存缓存

8.1两项已定夺事项（V1.1）

① 不返回 reasoning

决定：不返回。它是模型的自述文本，价值在于解释「为什么这么写」， 但两条理由压过了这份价值：

  • 内容不可预期。模型可能在思路里复述 schema、口径定义甚至表结构 —— 而 §4.2 刚刚把 schema_prompt 挡在接口之外， 再从 reasoning 漏出去等于白挡。
  • 它不是判定链路的一部分。本接口要回答的是「护栏做了什么判断」， 那是代码判定的记录；模型自述属于另一类信息，混进来会让人误以为 它也是可信的判定依据。

真要看模型思路，命令行仍可从检查点取到 —— 那条路径的使用者本就有服务器权限。

② trace_id 维持 12 位十六进制

决定：不加长。但理由必须写清楚，因为它不是「12 位本身够安全」：

项值
取值空间1612 ≈ 2.8 × 1014
限流上限（§5.1）30 r/min ≈ 4.3 × 104 次/天
穷举期望耗时约 6.5 × 109 天
限流是这个长度成立的前提，不是优化项 12 位之所以够用，完全依赖 §5.1 那条 30 r/min 的限流。 若将来有人以「回放接口太慢/太紧」为由放宽或去掉限流， 这个长度的安全论证同时失效 —— 两者必须一起改，不能单独动其中一个。 加长到 16 位会改变已有审计记录与检查点的 thread_id 格式， 需要一次性迁移，收益不抵成本。
