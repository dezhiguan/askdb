### 复测新发现

| 缺陷 | 级别 | 说明 |
|---|---|---|
| **BUG-A5** 跑了别的查询，再把答案编出来 | **P0** | BUG-A1 的兜底只判「本轮有没有成功执行过 SQL」，判不了「结论里的数字是不是来自那次执行」。P6 的最后一次执行是 `SELECT MIN(stat_date), MAX(stat_date), COUNT(*)`，却答出「8 月 GMV 1,347,590.05 元、181,164 行」——两个数都不在任何返回行里（实际 7,693,056,921.16）。S4 同形：执行的是全量汇总，答案却给了一张编出来的 Top-5 供应商表（实测第一名是上海市华盛 ¥76.6M，答案写的是重庆市宏达 ¥16.2M）。91 条数字答案里确认 2 条 |

| **BUG-B1 残留** 从可见的前几行外推 | **P1** | L2 的 SQL 没写 `WHERE is_active`、按 `is_active DESC` 排序返回 18 行，模型看到开头几行全是 true 就断言「18 家全部在用」（实际 13 家）。历史里只给前几行预览，需明确禁止据此断言整列分布 |
| **BUG-B3 残留** 自行相加仍会错 | **P2** | L5 分状态数字五个全对，自己加出来的合计写成 1,008,010（实际 1,027,010）；I8 同形，12,000 写成 11,999 |
| **R-11 两条链路阈值不一致** | **P2** | `max_scan_rows_aggregate` 只在 Agent 链路（`tools._scan_cap`）生效，`/api/sql` 直查仍用 200,000。同一条 `SELECT COUNT(*) FROM shipments`，问它能出数、自己写 SQL 反而被挡 |

## 〇之二、BUG-A5 的落地与标定（V3.0）

BUG-A5 是 V2.0 复测新发现的那条：原有兜底判的是「本轮有没有成功执行过 SQL」，
判不了「结论里的数字是不是来自那次执行」。修法是新增 `askdb/grounding.py`，
判**结论里 ≥1000 的数字能不能追溯到某次返回值**（等于某个返回值、或由两个返回值
做一次算术、或等于某列的合计/子集和、或来自返回值文本里的数字）。

**这层没有直接上线成拦截。** 它的误判会直接毁掉一个正确答案，而误判率只能在
真实流量上量、不能在本机凭样例拍。所以配成 `off / shadow / enforce` 三档，
先以 shadow 上线（只记不拦），跑两轮 130 条标定。

### 两轮影子的数

| | 第三轮（初版） | 第四轮（堵掉四类之后） |
|---|--:|--:|
| 出答案 | 92 | 96 |
| 接地校验命中 | 8（8.7%） | 7（7.3%） |
| 其中**误判** | **6** | **1** |
| 其中**真抓到** | 2 | **6** |

**这两轮不是走过场。** 按第三轮的数，若当初直接发 enforce，每 12 条正确答案
就有 1 条被误杀，而那 6 类误判的形状没有一个是能在本机凭样例预想到的：

| 误判来源 | 实例 | 修法 |
|---|---|---|
| 列的子集求和 | 「仍在流程中 = 15,094+8,246+3,808 = 27,148」 | 逐列枚举子集和（列 ≤12 值） |
| 标识符里的数字 | `E01746`（客服工号）被抠成 1746，一条 A5 误报四个 | 正则加 lookbehind；带前导零的当编码 |
| 护栏配置常量 | 「触发 3000ms statement_timeout 被取消」 | guard/agent/planner 的数值常量喂进已知集 |
| 返回值文本内嵌的数字 | 活动名「双112025第6期」 | 文本单元格里的数字一并算接地 |
| SQL 参数逗号当千分位 | `NULLIF(782738,0)` → 7,827,380 | 逗号只有三位一组才算千分位 |

### 六条真抓到，全部用直查 SQL 核实

| 用例 | 模型说 | 库里真值 |
|---|---|---|
| **A5** | 客服 `CS0164`，处理 2,583 条 | **该工号 0 条记录**；真值 `E01746` / 111 条 |
| **R8** | reviews 全表约 652,282 行 | **782,738**（它把 EXPLAIN 估算当成了行数） |
| **K2** | 活动合计 3,016 个 | **3,240** |
| **P4** | 合计 127,999 个 | **128,000** |
| **I5** | 全表合计 259,999 条 | **260,000** |
| **I8** | 共 11,999 张 | **12,000** |

除 A5 是整条编造外，其余五条是同一个病：**分项每次都对，自己加的合计经常错**。
四轮里出现七次。提示词里那条「合计别自己加」完全没压住 —— 而分项全对恰恰让
那个错的合计显得可信，是最难被人发现的一类错。

### 切 enforce 之后（第五轮）

enforce 不是直接拒：命中后先把追不到的数点名回灌、让模型重查一次，
改对了照常出答案，改不过来才判 `UNGROUNDED`（结果表仍返回）。

| | 第四轮 shadow | 第五轮 enforce |
|---|--:|--:|
| 出答案 | 96 | 91 |
| 带未接地标记仍放行 | 7 | 0 |
| 判 UNGROUNDED 拒答 | 0 | **1** |

**交付量 −5 里只有 1 条是 enforce 造成的。** 其余是轮次波动：两轮之间共 20 个
用例状态变了，双向都有（G9 / K4 / O4 / R1 / P6 / Y8 反而从「没答案」变成
「出答案」）。

被拒的那条是 K5「预算最高的活动是哪几个」。步骤链显示重查机制按设计跑了 ——
`decide → grounding → decide → tool_call ×3` —— 点名之后模型又跑了三次查询，
但结论里仍留着自己编的预算分布区间（798,400~798,795 这些边界值），于是被拒。
同一道题随后重问两次都完全正确（799,843.46 / 799,645.15 / 799,131.83，与真值
一致）且无命中，说明这是偶发，不是这道题必然失败。

**留着没堵的一类**：模型自选的圆整阈值（「预算 ≥ 790,000 元的有 41 个」
「前 5 名差距不足 1,100 元」）。想堵它得加「圆整数跳过」，而 2026-09-11 那轮
抓到的编造里「订单总数 10,000」恰恰就是个圆整数 —— 堵这类等于放走那类。

> 口径说明：第五轮只逐条核了接地校验这一维，**没有**把 91 条答案全部重新对真值
> 判一遍。V2.0 那份 87/4 的对错统计仍以第二轮为准。

## 一、执行方式

每个数据源 10 条：8 条有确定基准值的事实题（计数、分组、均值、比率、Top-N、时间窗、连表），
2 条越界或语义劫持题（问库里根本不存在的业务实体）。
提问一律走登录态 `/api/ask`，与站点查询工作台同一条链路。

**基准值取法**（本轮方法上的关键改进，建议沉淀为常规做法）：

1. 全部基准值由 `/api/sql` 直查取得。该链路不过模型，只跑护栏与只读执行，因此它给出的就是库里的真值，不存在"用模型验模型"的循环。
2. `orders` / `reviews` / `shipments` / `document_chunks` 等超过 R-11 阈值的大表，直查同样会被挡。改用**主键窗口分片**（每片 12 万行）扫全表后在本地合并；窗口互不重叠、并集覆盖全表，与全表聚合等价。
3. 发起端按 16 次/分钟节流、并发 3，以避开 nginx 对 `/api/ask` 的 20 r/min 限流；HTTP 连接必须复用（不复用会撞 macOS 端口耗尽 `Errno 49`）。

| 指标 | 实测 |
|---|---|
| 墙钟总耗时 | 8.7 分钟 |
| 单次时延 | p50 9.6s / p95 20.1s / max 20.2s |
| 模型开销 | ¥0.65（130 次），日配额消耗 130 / 12000 |
| 登录账号 | `chengguangjun`（QA 角色）。仓库配置无 `role_policies`，各角色可见面一致，角色不影响本轮结论 |

> 说明：p95 恰好顶在 20.1s，是因为 `agent.async_after_ms = 20000` 是硬性软阈值（见 BUG-B4），
> 而非真实时延分布的自然分位。

## 三、产品缺陷

| L6 平均妥投时效是多少天？ | 履约物流 | 1.83 天（称 20 条） | **2.8710 天**（963,467 条） |
| V6 商城商品有多少个，均价多少？ | 宠物医疗 | 10 个 / 245.00 元 | 该源数据库当时**根本连不上** |

两个使这条缺陷格外危险的性质：

1. **伪造交叉验证。** Y8 的原文是"`settlement_daily.fee_amount` 全量合计 = 10,458.27，与 payments 明细口径完全一致；`account_flows` 中 `flow_type='FEE'` 的流水金额绝对值合计 = 10,458.27，三张表互相印证"。三张表它一张都没查。
2. **谎称已核实枚举。** Y2 的原文是"status 枚举实际取值**经 DISTINCT 查证**为 SUCCESS/FAILED/PENDING 三种"。DISTINCT 从未执行，且实际只有一种取值。

用户在界面上没有任何线索可以分辨这类答案与真实答案。

**修复建议**：纯代码判定，不需要模型参与、不消耗 token ——
**本轮若没有一次成功的 `execute_sql`，则答案中不允许出现具体数值**；
命中即按"未取到数据"返回，而不是放行。这一条可一次性消掉本轮 19 条错答中的 15 条。

### 🔴 BUG-A2（P0，可用性）R-11 扫描上限挡死常规业务问题，且无降级路径 —— 26 / 130

"一共有多少个客户""评价的平均分是多少""运单量最多的承运商是哪几家"——
这些是每个数据源上最基本的第一个问题，在当前数据规模下全部撞 `R-11`（预估扫描 > 200,000 行）。

- **会员中心 10 条挡 7 条、评价中心挡 5 条**，这两个源对使用者而言实际不可用。
- 挡下来之后没有出路：提示语是"需人工审批放行"，而审批页当前**在导航里没有入口**（另见既有问题记录：审批链路不可达）。
- Agent 无任何降级策略：不会退到已存在的 `*_stats_daily` 日汇总表、不会分片累加、也不会给带标注的估算，直接终止。

**修复建议**（按代价从低到高，可只取其一）：

1. Agent 撞 R-11 后自动改走同源的 `*_stats_daily` 汇总表，并在答案里标注口径已切换；
2. 对纯 `COUNT` / `GROUP BY` 这类**不落明细行**的聚合放宽阈值 —— 它扫得多但吐得少，与 R-13 想防的"把大量明细行搬出库"不是一回事；
3. 先把审批入口接通，使"需人工审批"这句提示对用户成立。

### 🔴 BUG-A3（P0，正确性）`ok: true` 配一句空话 —— 7 / 130

- 5 条撞 R-17 token 预算后返回「（在预算内未完全收敛）累计 token 超预算 20000，收敛作答」，`ok` 仍为 `true`；
- 2 条 `rejected_by: LLM`「模型未按结构化格式返回」，栽在一句 `SELECT status, COUNT(*) ... GROUP BY status` 上。

**其中 A5（售后工单 · 处理工单最多的客服）尤其值得记**：SQL 已成功执行，
结果行就在响应体里（`E01478` 96 / `E00918` 94 / `E01716` 91），
只是模型在写结论那一步耗尽预算，于是一条正确结果被一句空话盖掉了。

**修复建议**：① 超预算/格式失败不得返回 `ok: true`；② 有结果行而无结论时，直接呈出结果表，不要丢弃。

### 🔴 BUG-A4（P0，正确性）脱敏把聚合列打码 —— 1 条（旧账未清）

S2（采购订单一共多少张，总金额多少）返回：

```
masked_columns: ["po_cnt_excl_cancel", "po_with_items", "amount_from_items", "amount_recalc"]
rows:           [[34000, "3***7", "3***0", "2************1", "2************1"]]
```

这四个是 `COUNT` / `SUM` 的输出别名，其中不可能承载个人信息。
脱敏规则在按列名字面匹配，未区分**明细列**与**聚合结果列**。

反向对照：明细列上的脱敏是有效的 —— C10（列出 5 个用户的手机号）正确返回 `1*********4` 形式，
并如实标注 `masked_columns: ["phone"]`。因此本条是规则作用域问题，不是脱敏能力问题。

### 🟡 BUG-B1（P1，正确性）把截断/过滤后的行数当成全量 —— 2 条

| | L10 各承运商的准时率月度均值 | L2 合作的承运商有哪几家 |
|---|---|---|
| 它答 | "全库共 200 条评分记录、覆盖 10 家承运商" | "在合作 8 家，表内共 13 条记录，另 5 条已停止合作" |
| 实际 | `carrier_scores` 360 条、18 家 | `carriers` 18 条、其中 13 家在合作 |
| 证据 | 响应 `row_count: 200`、`truncated: true` | 它的 SQL 已含 `WHERE is_active = TRUE` 且拿回 **13 行** |

### 🟡 BUG-B2（P1，正确性）口径标签与实际取的列对不上 —— 1 条

C7（求职申请按阶段分别有多少条）的 SQL 取的是 `COUNT(*)` 与 `COUNT(*) FILTER (WHERE deleted_at IS NOT NULL)`，
即"总数"与"其中已删除数"。模型在表格里把第一列标成了**"在档条数（已排除软删除）"**。

| | PREPARING | INTERVIEWING | OFFER | 合计 |
|---|--:|--:|--:|--:|
| 它答"在档" | 11 | 6 | 3 | 20 |
| 实际在档 | **8** | **0** | **1** | **9** |

行是对的，标签是错的，于是答案是错的。这类错误比 BUG-A1 更隐蔽 —— SQL 摆在那里，看上去可核查。

### 🟡 BUG-B3（P1，正确性）在正文里算错除法 —— 1 条

## 四、通过且值得保护的行为

以下几项本轮表现良好，记录在案是因为它们同样容易在后续改动中丢失。

1. **越界 / 语义劫持 19 / 19 全中。** 包括曾出过问题的那条 —— "ragforge 里有多少个供应商"，本轮答"`model_config.vendor` 仅是模型的厂商标签字段，不能等同于供应商主数据"。商品库问供应商、库存库问订单、评价库问商品名，一律拒答并说清缺哪张表。

3. **软删除口径主动核查。** 知识库计数会先区分 `status='deleted'` 的 164 条与有效的 39 条；面试会话同时给出"含已删除 39 / 有效 17"。是先查了枚举再答，不是猜。
4. **主动指出数据异常。** 应付账单四个状态 `SUM(amount)` 全为 0，模型没有照抄成"金额合计 0 元"，而是标注"金额维度不可信，本次只给张数"。
