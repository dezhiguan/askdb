结论

三项指标的可达目标，按下面逐条论证的改动累加得出。改动 1 是确定性代码闸，改动 2–4 是提示词与注入层调整、须影子跑标定，所以给的是保守口径。

⚠ 这三个数已被实测证伪，看 §09

六条改动已于 2026-09-15 全部落地。23 条生产真实提问的两档对照（只看两档都出数的 15 条）实测收益是 tok_in −16.5%、成本 −19.0%，而 tok_out 反而 +6.7% —— 不是下面这三张卡上的 −71% / −71% / −68%。其中 P0-3 被算成 51% 耗时、43% 成本的那一大块，量级没有被证实。

原因不复杂：下面这三个数是拿一条 trace 算的，而那条跑了 6 轮 decide， 对照组的中位数只有 4 轮 —— 可省的部分从一开始就没有它显示的那么多。 这正是本节下方那条口径提醒说的事，只是当时还只是提醒。 三张卡原样保留不回填，它们是当时的估算依据，改掉就失去了对照价值。

第 02 步模型选了 search_schema，第 03 步 _n_act 的 ⓪′ 兜底把它挡下了，span 状态 degraded、输出 {"reused": true}、耗时 0 ms。兜底省掉了重复的 embedding 调用，但没省掉那一轮决策本身 —— 2,940 ms 和 4,355 个输入 token 已经花出去了。

18 行 × 每行 20 个月、首尾月份完全一致 —— "共 360 行 = 18 家 × 20 个月、无重复无缺失"这个结论此刻已经成立了。但模型又跑了两轮去"确认"：

第 07 步 → 返回 1 行：360, 18, 20, 360
SELECT COUNT(*), COUNT(DISTINCT carrier_code), COUNT(DISTINCT score_month),
       COUNT(DISTINCT carrier_code || '#' || score_month::text) FROM carrier_scores

第 09 步 → 返回 20 行，每行都是 18, 18
SELECT score_month, COUNT(*), COUNT(DISTINCT carrier_code)
FROM carrier_scores GROUP BY score_month ORDER BY score_month

成因不是模型笨，是提示词在要求它这么做。AGENT_SYSTEM 的硬约束第 2 条写着"要陈述某张表一共多少行，必须单独跑一次不带过滤的 COUNT"，第 6 条写着"要判断整列的分布或总量，另跑一条 GROUP BY"。模型的答案里主动写了"共 360 条记录""每个月都恰好有 18 家"，于是这两条规则各收了它一轮。护栏本身是对的（它们是从真实错答里挣出来的），错的是"单独跑一次"这个措辞把核对钉死成了额外一轮。

代价：5,089 ms · 10,863 in / 249 out · ¥0.002727

重复 C最后一条 SQL 把第一条整个重算了一遍

第 11 步这条查询重新算了一遍 AVG(on_time_rate)，并加上了"最近一月"和"近 3 月均值"两列。它是第 05 步那条的超集 —— 也就是说第 05 步的结果被自己作废了。而多出来的两列，用户没问。

这一轮不是纯浪费 —— 多给一列对比往往是好产品行为。问题在于它是靠"多跑一轮"拿到的，而不是在第一条 SQL 里一次写完。同样的两列写进第 05 步那条查询，边际成本是 0 ms、0 token。

代价：4,768 ms · 5,931 in / 242 out · ¥0.001712

重复 D收敛轮把界面已经渲染好的结果表又抄了一遍

第 12 步输出 1,415 个 token，其中主体是一张 18 行 × 6 列的 Markdown 表。这张表的数据就是 last_exec 里的结构化行，前端结果区本来就在渲染它。模型把它逐格重打了一遍 —— 而且是在 with_structured_output(method="function_calling") 的 JSON 参数里，换行全被转义成 \n，还额外胀了一成。

按 1,415 tok / 18.1 s ≈ 78 tok/s 的解码速率算，这一张表就是十几秒。而且 structured() 走的是非流式 invoke，这 18 秒里界面上一个字都没有。

代价：约 12,000 ms · 965 冗余 out token · ¥0.002606

附带发现analyze_result 在这条链路上只可能亏

它的设计意图是"不回库、省一次数据库往返"。但这条链路上 4 次 SQL 执行合计 90 ms，而让模型选中这个工具要付一整轮决策 —— 2–3 秒 + 四五千 token，去省 20 毫秒。这个工具在当前的成本结构下无论怎么用都是负收益。本次链路它一次都没被调用，算是走运。

04优化方案

按"确定性 > 概率性"、"改代码 > 改措辞"排序。P0 三条互不依赖，可以并行落；P1 需要影子跑标定后才切；P2 是结构性的，单独立项。

P0-1按问题类型决定要不要把 search_schema 摆上桌代码 · 确定性

不动 NO_EVIDENCE 那道闸的判据（那是另一个该单独标定的改动，而且已经被 test_agent_no_evidence_blocks_fabricated_number 拦过一次），改为只在真正需要它的那类问题上暴露它。

怎么改：① 在 agent.IntentCheck 上加一个字段 metadata_only: bool（"问的是库/表/字段本身，而不是表里的数据"）—— intent 那次调用本来就在跑，多一个字段只增约 10 个输出 token。② agentgraph._hidden_tools 改成：schema_complete and not metadata_only 时，把 search_schema 一起收进 hide。

元数据问题照旧留着 search_schema，闸 ① 保护的正是这一类，行为完全不变；数据问题必然要跑 execute_sql，闸 ① 天然满足。_n_act 的 ⓪′ 硬兜底原样保留，收暴露面从来只是引导。

做法上有取舍：with_structured_output 流式解析局部 JSON 是可行的但脆；更稳的是让收敛那一次走两段——结构化调用只返回 finish/thought 和一份要点提纲，再用非结构化流式调用写正文。但那会多一次调用，与省成本的目标冲突。建议先做 P0-3 把输出压到 450 token（届时这一步约 6 秒），再评估是否值得为流式付一次调用。

原提法：本次召回 12 张表 / 5,103 字符，真正用到的只有 carrier_scores 和 carriers（648 字符），87% 是陪跑的；那就只给相似度前 3 名完整列级明细，其余只给表头。原文已把它列为"前置：先在向量路径上补一份 recall@k 基准，否则这个改动没有判据"。

基准跑完了，判据是否定的 —— 这条不做。见 test-report-schema-recall.md（97 条 / 12 源，向量路径首次实测）：

主表口径 recall@k（96 条，问题里不含表名）
  k=1    40.6%
  k=2    65.6%
  k=3    74.0%  ← 分层注入要押的就是这一格
  k=5    86.5%
  k=8    95.8%   ← 现行 top_k，曲线到这里才进平台区
  k=12   97.9%   ← 现行 max_k，收益已递减

按前 3 名分层，四分之一的问题里真正要写进 SQL 的那张表拿不到列名。放宽到前 5 名也还有 13.5%。而现行的 top_k=8 / max_k=12 恰好落在曲线转平的位置 —— 这组参数是对的，不要往下调。

更要紧的是落榜的形状：主表排不进前 3 的 25 条里，25 条的主表全部是各自领域的枢纽表 / 主实体表（documents×8、knowledge_bases×3、retrieval_logs×3、resumes×3、agent_sessions×2，以及 users、organizations、skus、payments、purchase_orders 等），没有一条是冷僻表。分层注入会精确地砍掉最该保留的那一批。

结论
不做。同时确认 top_k=8 / max_k=12 / token_budget=4000 维持不动。

P2-3召回基准顺带挖出来的三件事新增 · 由 P2-2 的基准派生

基准不只是否掉了一个提案，它把召回的三种失败形态各钉出了实探。这三条都不是性能问题，是答案正确性问题，优先级应当高于本方案里的任何一条省钱改动。

① 2.1% 的题，主表连注入集都进不去

【careermate】有多少用户创建过简历但从没发起过会话   → users 第 27 名
   1. resume_generation_run  0.7048
   2. agent_pending_actions  0.6353
   3. interview_sessions     0.6344
  ...
  27. users                  0.4397

问题里的名词是"简历""会话"，描述里复述这些名词的卫星表全部压过 users —— 而 users 才是被计数的主体。第 27 名意味着它根本不会出现在提示词里，模型只能在给它的 12 张里硬凑。同类还有 ra-j11（organizations 第 16 名、相似度 0.32，低于 min_score）。这是静默答错的风险位。

② 预聚合表压过明细表 —— 已有现成解法没铺开

【shop_supply】逐个供应商统计采购金额并排序   → purchase_orders 第 7 名
   1. purchase_stats_daily   0.7243
   2. suppliers              0.6899

这个坑在 shop_logistics 上已经填过：logistics_stats_daily 的表注释里写着"只用于看趋势；要查哪些运单…用 shipments"，shipments 也写了反向指路 —— 而 shop_logistics 两条用例的主表 @1 都是 100%。把这句话照抄到 purchase_stats_daily 等同构表上，成本极低。（n=2，方向明确但不构成因果证明。）

③ 向量召回没有字面锚点

【ragforge】JD 文档数是多少            → documents 第 7 名
   1. judge_metrics_daily  0.4476   ← "JD" 被吸到了 "judge"

【ragforge】documents 表一共有多少行   → documents 第 2 名
   1. document_chunks      0.4915   ← 问题里逐字写着表名，仍被压过

问题里原样写出表名也不保证第一名。第一例正是生产上那条已知缺陷（「JD 数」恒 0）的召回侧证据 —— 此前只知道列注释缺失让模型选错了列，现在看到召回这一层就已经把主表排到第 7 了。建议：问题命中表名或别名时给一个确定性加权，别让向量单打独斗。

红线与收益指标

  • 三档旋钮。每条提示词改动配一个 off / shadow / enforce 开关，与 agent.grounding、agent.grounding_no_exec 同一套语义。shadow 下不生效判定，只记指标。
  • 不许恶化的红线（任一触线即不切）：接地校验 ungrounded 命中率、rejected_by=R-11 比例、OOS 拒答率、同义问法一致性。前三个是安全性，第四个是这个产品此前就吃过亏的地方。
  • 要看的收益指标：baseline.json 的 avg_steps（目标：本条链路 6 → 2）、p95_ms、avg_tok、avg_cost_cny、cache_hit_rate。
  • 样本量。对照组 23 条只够看链路健康。判定类改动（P0-2 / P0-3）仍要按老规矩在生产真实流量上跑两轮、每轮不少于 130 条、覆盖全部 13 个数据源，别只在 履约物流 上验。

07顺带查出来的一个账面缺口

账面embedding 成本没有进 trace

agentgraph._n_recall 落 schema_recall span 时只传了 tables / input / output，没传 cost_cny —— 而 tools.search_schema 的返回体里 embed_tokens 和 embed_cost_cny 都是现成的。

结果就是这条 trace 的 ¥0.012834 里不含那次向量召回的 embedding 计费（text-embedding-v4，¥0.0005/千）。金额很小，但方向是错的：做成本优化的前提是账面完整，而 trace.embed_cost_cny 的注释自己就写着"不设默认价，0 元在成本页上是显眼的、会被人问起来" —— 这里正是那个该被问起来的 0。

修法：_n_recall 的 tracer.add 补上 cost_cny=rec.data.get("embed_cost_cny", 0) 与 tok_in=rec.data.get("embed_tokens", 0)。一行的事。

确定性的三条，每次都成立

  • P0-1：全部跑测里 tool_call · search_schema 出现 0 次。
  • P1-2：analyze_result 出现 0 次。
  • 账面：schema_recall 那一格真的有钱了，记在 text-embedding-v4 名下。 此前这里写的 3,649 token / ¥0.0018 是错的 —— 那是本机首次跑、正在**建索引**时量到的。生产稳态下索引早已建好，每次只嵌入问题本身： 2026-09-15 线上 trace 1661c5593c76 实测 15 token、 约 ¥0.00001。账面缺口是真的（此前记 0），但**比原先报的小约 100 倍**； 连带地，"on 档含 embedding 所以真实差距更大"那句话也不成立 —— 这笔钱可以忽略。
  • 结果区取数：专项复跑 5 次，4 次链路上存在"返回 1 行 / 20 行 / 200 行"的探查查询， 每次渲染的都是那条 18 行的作答查询；其中一次最后那条 SQL 还执行失败，照样取对。

本机这套数的两处污染，别拿去当生产值

① 到百炼的 RTT 是 460ms（vpn-bypass 只放行了三台服务器 IP，模型流量仍走公司隧道； 一次最简单的 embedding 调用要 1.8 秒）。叠加 356266f 刚把单次调用超时砍到 20 秒， 本机约 13% 的调用以 LLM 失败告终 —— 那是环境，不是代码，生产在同区域内网。 所以耗时那一列不具代表性；token 与成本是服务端计数，不受影响。

② 这仍然不是验收。本机同种子库、无并发、绕开了 HTTP 与长任务交接 （/api/tasks/{id} 无条件要登录，而 async_runner 在 step≥3 必然交接）。 生产验收仍按 §06 跑 evals/baseline.py。

P2-3 的根因，在生产上得到确认

源别名行表头样例

连带一个坦白：别名解析那条改动对生产几乎没有作用。它落在 whitelist_from_scan 里，只在重新扫描数据源时跑 —— 已登记的源存的仍是旧白名单；而 ragforge 即便重扫，它本来就没有注释可解析。 真正有别名的 shop_* 系列，注释里那些别名早就作为 desc 文本进了提示词与嵌入， 解析成结构化字段带来的增量，正是基准量到的那 +1.0 个点。
