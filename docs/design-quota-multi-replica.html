1现状与动机

1.1现在怎么算的

# graph.ask() —— 在任何模型调用之前
used = today_calls(cfg.audit_log)      # 数当天审计日志的行数
if used >= cfg.daily_quota:
    return AskResult(ok=False, rejected_by="QUOTA", …)

这套设计带来两条硬约束，都写在了编排里：

约束原因代价
replicas: 1计数是单副本的本地文件，多副本各算各的实际额度变成 N 倍，且无法横向扩容
审计日志必须挂持久卷Pod 重启计数归零已用 hostPath 解决，但把 Pod 钉在了单节点上

1.2改成什么

现在 入口处数审计文件行数 → 单副本、单节点 改后 模型调用端 INCR Redis 计数器 → 多副本、可横向扩容

2语义变更 —— 本设计影响最大的一处

「一次配额」的含义变了，不只是换了个存储 现在在入口计数：一次提问 = 1 个额度，无论它内部调了几次模型。
改到模型调用端后：一次提问消耗的额度 = 它实际发生的模型调用次数。
问答形态实际模型调用现在扣改后扣
单步、一次过111
单步 + 2 次反思重试313
多步（3 步，含规划与评估）最多 91最多 9

这个变化是好的，而且是本设计的主要收益之一。配额的目的是控成本， 而成本由模型调用次数驱动，不由提问次数驱动。 现在一个多步问答花的钱是简单问答的 9 倍，却只扣 1 个额度 —— 配额与成本脱钩，等于给了一条"用复杂问题绕过配额"的路径。

但配额数值必须跟着调 实测样例库上多数问答是单步一次过，但按最坏情况（多步 9 次）估， daily_quota: 200 在语义变更后可能只够 20 多次提问。 上线时须同时把数值调高（建议 500），否则用户会感到额度"莫名其妙少了"。 这一条不是可选项 —— 语义变了而数值不变，等于悄悄收紧了服务。

3计数设计

3.1落点

计数放在 LlmClient 真正发起请求之前 —— 那是唯一会花钱的地方。 反思重试、多步规划、评估节点，全都经过它，无需在每个调用点各写一遍。

# 实现：askdb/quota.py，扣减点在 LlmClient.structured() / generate_sql() 入口
key = f"{key_prefix}:{今天日期}"     # 对外实例为 askdb:quota:public:2026-08-14

key_prefix 由配置给出，让对外实例与内部实例各算各的额度，互不影响。 选哪个后端只看一条规则 —— 配了 quota.redis_url_env 指向的环境变量就用 Redis， 没配就退回本地文件（本机开发只有一个进程，文件计数是对的）。

不做「Redis 连不上就自动退回文件」的降级 那会让多副本部署在 Redis 抖动时静默变成每个副本各算各的 —— 正是本设计要消灭的那个问题，而且没有任何外部迹象。 要么用共享计数，要么明确知道自己在用本地计数，不要中间态。

备选模型也照扣：主模型失败后切备选是又一次真实的厂商调用，不扣等于失败重试不要钱。

3.2原子性：Lua 预扣

不要「先读后写」 GET 判断再 INCR 是典型竞态：多副本并发时会同时读到 199 然后各自加一，双双放行。判断与自增必须是一步。

初稿打算用「无条件 INCR，拿返回值判断，超限不回滚」。 它确实没有竞态，但有个副作用：被拒的请求也让计数继续涨 —— 一个脚本在额度用尽后持续打，计数会一路涨到几万， 「今日剩余」和运维看到的用量就都不再是真实调用次数。 实现改成用一小段 Lua 把「读-判-增」合成一步，超限时不增：

local used = tonumber(redis.call('GET', KEYS[1]) or '0')
if limit > 0 and used >= limit then return -1 end   -- 拒绝，且不计数
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ttl) end
return n

Lua 在 Redis 里单线程执行，整段不可分割，所以既没有竞态， 计数也永远不会超过上限。实测：上限 3 连扣 5 次得 1, 2, 3, -1, -1，且 TTL 只在首次 INCR 时设置。

TTL 取 48 小时而不是「到今日 24:00」：跨天由键名里的日期决定， TTL 只负责回收旧键 —— 给足冗余比算得精确重要。

3.3Redis 不可用时怎么办

这是本设计最关键的一个取舍：

策略后果采用
fail-open（放行）计数失效，模型调用不再受限 —— 对外实例可能被刷爆，而这正是配额存在的唯一目的否
fail-closed（拒绝）自然语言问答不可用；直查 SQL 不受影响，护栏、改写、干跑、执行全部照常是

与既有原则一致：tenant.on_unresolved: reject、 配置校验 fail-closed、§4.5「不做静默降级」—— 本项目一贯的选择是「宁可不可用，不可不设防」。

降级后的用户提示必须说清楚 不能只显示「服务不可用」。应明确：「用量计数服务暂时不可用， 自然语言问答已暂停；直查 SQL 仍可使用」 —— 让人知道发生了什么、还能做什么，而不是以为整个站挂了。

实现上做成配置项 quota.on_backend_error（block／allow）， 默认 block，配错值也回落到 block —— 「配错就悄悄变成放行」是这里最危险的默认。

读与写的取舍不同，别用同一套 只读探测（页面展示「今日剩余」、入口快速失败）后端异常时返回 0，不打挂请求； 真正的把关只在预扣那一步，它不会因为读失败就放行。 读的失败方向可以宽松，写的不行。

顺带纠正一条当时给出的错误建议：「先把各服务配置改好、验证能连，再设密码」 行不通 —— 实测对免密 Redis 执行 AUTH 会直接报错， 所以只能先设密码、后重启服务，中间必然有一段不可用。

5多副本还差什么 —— 配额只是其中一条

初稿这一节判断错了，据实更正 V1.0 写「检查点／审计日志每个 Pod 一份本地文件」—— 这是错的。 卷是 hostPath: /opt/askdb/var，单节点 k3s 下所有 Pod 挂的是宿主机上 同一个目录、同一份文件。
所以真正的问题不是「各存各的、续跑时灵时不灵」（那反而不会发生）， 而是多个进程并发读写同一份文件：SQLite 争锁、JSONL 撕行。 这两个是有确定解法的，不需要等检查点换 PG 后端。
组件现状多副本后处理
每日配额数当天审计日志行数，本地文件失效改 Redis 共享计数。本设计
检查点
（SqliteSaver + hostPath）		各 Pod 共享同一个 SQLite 文件；默认 DELETE 日志模式下写阻塞读，抢不到锁立刻报 database is locked会争锁开 journal_mode=WAL（多读+单写并行）+ busy_timeout=5000（抢不到锁等 5 秒而不是当场失败）。前提是本地盘 —— 网络盘上 WAL 不可用
审计日志各 Pod 追加同一个 JSONL；带缓冲的写可能把一条记录拆成多次系统调用，两个进程的片段交错落盘会撕行绕开 Python 缓冲层，O_APPEND 下用单次 os.write() 把整行交给内核（该场景下定位与写入是原子的）
样例库随镜像固化，只读无影响各副本一份完全相同的只读副本

结论：三条都已落地，replicas 于 2026-08-14 放到 2。

但这三条都依赖「单节点、同一个 hostPath」 WAL 要求同机本地盘，O_APPEND 原子性要求同一个 inode。 一旦跨节点，三条全部失效 —— 那时检查点得换 Postgres 后端、 审计得换集中式收集，不能只把 replicas 调大。 编排文件里已把这个前提写在注释里。

7风险与未决

等级事项处理
高新增一个硬依赖。fail-closed 意味着 Redis 挂了自然语言问答就不可用这是刻意选择（§3.3）。直查链路不受影响，降级面可控
中共享 Redis 的淘汰策略是 allkeys-lru（maxmemory 384mb）。内存打满时配额键会被淘汰，计数静默归零未处理。当前全库仅十余个键，实际风险为零。要根除得把策略改成 volatile-lru，但那会影响另外三个服务，不宜为 askdb 单方面改动
中多副本依赖「单节点 + 同一个 hostPath」（§5）跨节点时 WAL 与 O_APPEND 原子性同时失效。编排注释已写明，扩到多节点前必须先换检查点后端
低共享 Redis 无密码已解决 2026-08-14 设 requirepass，见 §4
低跨时区：日期键按服务器本地时区切各副本同时区，口径一致；与改造前行为相同，不引入新问题

7.1评审结论（已确认）

  1. 配额新数值：500。按 deepseek-v4-flash 单次约 ¥0.0009 计， 满额约 ¥0.45/天 ≈ ¥13.5/月。其余配置按旧口径乘 3 折算，保持实际可用量不变。
  2. 给共享 Redis 加密码：做。已于 2026-08-14 完成，见 §4。
  3. replicas 放到 2。三处单副本假设（配额／检查点／审计）已一并解决， 节点实测内存已用 75%、单 Pod 实测 131 Mi，加一个副本余量充足。
