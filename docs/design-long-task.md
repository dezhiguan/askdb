## 0. 结论先行

**不新增"长任务"这个对象。** 系统里已有一条贯穿始终的主线：`thread_id`。
异步执行、中断续跑、审批、复核、补充条件，全部是这条线上的不同 **stage**，
由审计流水派生（`askdb/audit.py` 九档任务态 + `_NEXT_ACTOR`）。

"转长任务后还能不能恢复、能不能人工介入、是不是同一个流程"——
**本来就是同一个流程**，缺的不是模型，是零件没接上。

```
提问 ──> 同步执行 ────────10s────────> 交接：回执 thread_id，后台继续跑
           │                                    │
           │（节点边界随时可提前交接）            ├─ 进程被杀   ──> 检查点在 ──> 续跑（自愈/人工）
           │                                    ├─ 扫描超阈值 ──> 等审批 ──> 凭票继续
           └─ 10s 内跑完 ──> 直返结果            ├─ 条件不足   ──> 等补充 ──> 带新条件继续
                                                ├─ 结果存疑   ──> 等复核 ──> 采信/打回
                                                └─ 数据源故障 ──> 等运维 ──> 恢复后重试
                              （五个出口，同一条 thread_id，同一页任务中心）
```

## 1. 现状盘点（2026-09-13 代码为准）

### 1.1 已经具备的能力

| 能力 | 位置 | 状态 |
|---|---|---|
| 转后台异步 | `askdb/async_runner.py` + `server.py:3267` | 有，但只有入口墙钟一种判据，且只装在 `/api/ask` 上 |
| 检查点 | LangGraph PG saver（`graph.compile_with_checkpoint`） | 有，4 副本共享，跨 Pod 可续 |
| 续跑 | `agentgraph.resume()` / `POST /api/resume` | 有，两条路（活断点续 / 带新输入重跑）。**当前完全同步，无交接** |
| 续跑前重验 | `graph.precheck_resume` | 有。中断与续跑之间前提可能已变，不重验就是拿旧前提接着跑 |
| 可续跑判定 | `agentgraph.is_resumable`，与 resume 同源 | 有，避免"说能续、点下去 404" |
| 任务中心 | `GET /api/tasks`，审计派生 | 有，九档状态 + 下一步该谁动手 |
| 人工介入四档 | approvals / reviews / ops / waiting_input | 有，2026-09-12 已生产实测六档全通 |
| 陈旧兜底 | `_STALE_RUN_AFTER_S=900` + 检查点核实 | 有，僵尸线程改判等运维 |

### 1.2 转异步的现行判据（唯一一条，且只在一处）

`server.py:3271` 取 `agent.async_after_ms`，把 `run_agent` 提交到 8 线程池，
主请求 `future.result(timeout)`，超时返回回执、后台继续跑完写 final。

生产取值 **45000ms**，而实测 p50 = 9.6s / p99 = 30s —— 这条路在生产上几乎不触发。
`async_runner.py` 文档头承诺的 "Tier-1 预判（as_task / 多步 / 大扫描）走
threshold_ms=0" **代码里没有实现**；`as_task` 目前唯一作用是要求登录。

### 1.3 四个缺口（G1~G3 已于 2026-09-13 修复，G4 同日改为钉住策略）

- **G1 前端读不懂异步回执。** `QueryWorkspace.run()` 把 `{async:true, thread_id,
  message}` 当 `AskResult` 用：`value.ok` 为 undefined → 切到 SQL 页签、渲染空结果、
  「最近查询」标成 interrupted。**阈值降到 10 秒后这会是过半请求的默认体验**，
  所以它不是"要修的一个 bug"，而是本次改造的前置条件。
- **G2 后台任务没有进度。** 审计只在入口写 `PHASE_STARTED`、收尾写 final。
  **落地时改了做法**：进度取自**检查点**（`agentgraph.progress`），不往审计里插
  中间记录 —— 那会让统计口径、任务聚合、复核队列跟着变形，而这正是本仓库最容易
  漂的东西。图每过一个节点本就落一次检查点，step 与当前工具都在里面。
- **G3 进程被杀无自愈。** 异步池是进程内的，Pod 滚动更新会连带杀掉在跑的任务，
  之后等 900 秒陈旧判定，再由人点一下续跑。
- **G4 兑付窗口不一致。** 任务中心按最近 2000 条线程（实测约 35 分钟量级），
  审批队列 4 天。**落地时改了做法**：不放大窗口（那会把这一页拉回"全量读进内存"
  的老形状），而是把「还等着人动手」的线程**钉进**这一页 —— 未决的审批单、
  批了票还没用掉的那些，最多 200 条（`audit.TASKS_MAX_PINNED`）。

## 2. 什么情况下转长任务

### 2.0 统一交接点（本版核心）

**一条执行只有一个交接判据：从这次执行开始计时，墙钟超过 `async_after_ms`（10 秒）
就交接到后台。** 交接不是取消重跑 —— 已经花掉的步数与 token 全部保留，
变的只是"结果怎么送达"。

两条随之而来的约束：

1. **交接可以发生在任何地方，不只是入口。** 主请求线程在入口等 10 秒是兜底；
   图在**每个节点边界**也检查一次同一个截止时刻。谁先越线谁触发。
   节点边界那一路是必需的，不是冗余 —— 它让"跑到一半才发现会长"的任务
   立刻交接，而不是等主请求那个 timeout 兜底；对不经过入口等待的执行路径
   （下面第 2 条），它是**唯一**的交接点。
2. **每一个执行入口都要接上，不只 `/api/ask`。** 当前 `run_or_detach` 只装在
   `/api/ask` 上，于是这三条路一旦跑长就只能死等到 nginx 504：
   - `POST /api/resume`（续跑，`server.py` 直接调 `run_resume`）
   - 启动自愈续跑（§3.2 R2，本方案新增）
   - 审批通过后的代跑（§4.2 H1，本方案新增）

   续跑尤其要接：它恢复的本来就是一条已经证明自己跑得久的线程。

### 2.1 提前交接（不必等满 10 秒）

有些情况在 10 秒之前就已经能断定"这条会长"，早交接一秒就少占一秒连接：

| # | 条件 | 判据来源 |
|---|---|---|
| A-1 | `as_task = true`（显式创建任务） | 请求字段，入口即判，0ms 交接 |
| A-2 | 携带 `approval_id` 的凭票重跑 | 请求字段：它有票，正因为被判过大扫描 |
| A-3 | 数据源标记为慢源（`async_always`） | 源级配置：跨境源、脏 schema 源 |
| A-4 | 后台池水位 ≥ 6/8 | 池状态：高水位下同步等待只会一起拖死 |
| A-5 | planner 判 `multi_step`，或 `step >= 3` | 图内 decide 节点 |
| A-6 | 累计 token ≥ `cost_cap_tokens` 的 50% | 图内 `state.tok_used` |
| A-7 | 某步 EXPLAIN 预估扫描 ≥ `max_scan_rows / 2` | 执行器（未到 R-11 拦截线，但注定慢） |

A-5 ~ A-7 拿不到于入口，只能在节点边界判 —— 这正是 §2.0 第 1 条存在的理由。

### 2.2 不交接的

- 应答缓存命中：零模型零执行，在阈值之前就返回（`server.py:3248`）。
- `/api/sql` 直查：R-12 三秒硬超时兜底，天然不会长。
- R-11 拦截挂起：本就是立即返回一张待批的单子。

### 2.3 取值

| 环境 | `agent.async_after_ms` | 说明 |
|---|---|---|
| 生产 `config/public.yaml` | **10000**（现 45000） | 本次决策值 |
| 本机 `config/askdb.yaml` | 8000（不动） | 本机复杂链路本就跑得久 |

nginx `/api/ask` 的 `proxy_read_timeout 60s` 保持不动：10 秒交接后余量 50 秒，
504 这条路彻底走不到了。

## 3. 中断恢复

### 3.1 已经成立的部分（不动）

被杀的线程现场留在 PG 检查点里；任务中心按检查点核实后标 `resumable`；
续跑走 `precheck_resume` 重验前提 → 从最后一个完成的节点接着跑，已完成节点不重跑；
写**新 trace_id、同一 thread_id**，另计一次配额。4 副本共享检查点与审计，
所以 A Pod 上被杀的任务，B Pod 上续得起来。

### 3.2 要补的

- **R1 优雅退出。** 收到 SIGTERM：停止接新任务，给在跑的任务留一个节点边界的时间
  落检查点，超时才硬退。现在是直接连带杀掉。
- **R2 启动自愈。** Pod 启动后扫一遍 stale 且检查点可续的线程，**自动续一次**
  （每条线程最多自愈一次，写 `kind=auto_resume`，失败即转等运维）。
  否则每次发版都制造一批要人手点的僵尸任务 —— 10 秒阈值下在跑的任务只会更多。
- **R3 取消。** `POST /api/tasks/{tid}/cancel`：写取消标志，节点边界检查后收尾为
  `CANCELLED`。归属校验与续跑同一条。现在 detach 之后没有任何停止入口。

## 4. 人工介入（仍在同一条流程内）

### 4.1 现有四个停靠点（保持）

| 状态 | 谁动手 | 怎么回到主线 |
|---|---|---|
| `waiting_approval` | 系统管理员放行 | 发起人凭票重跑（票一次性、绑问题原文） |
| `waiting_review` | 系统管理员采信/打回 | 采信即终态；打回换个问法重新发起 |
| `waiting_input` | 发起人补充条件 | `/api/resume` 带 clarification，接在原线程上 |
| `needs_operator` | 运维 | 恢复后重试 |

### 4.2 要补的

- **H1 审批通过后自动续跑。** 现行闭环要求发起人回来点「凭票重跑」—— 对同步查询
  合理，对已交接的长任务不合理：发起人早走了。审批通过时若该 thread 有活检查点，
  由系统代跑（写 `actor=approval`，**配额仍记发起人头上**，那是他的消费）。
  显式开关、默认开：它改变了"服务端不替任何人执行"这条既有约束。
- **H2 图内请求补充（真正的 human-in-the-loop）。** 现在 `waiting_input` 只能在整条
  链路收尾后产生 —— 模型跑到一半发现口径不明，只能硬着头皮猜完再说。改成在 clarify
  节点走 LangGraph 原生 `interrupt()`：任务当场停在 `waiting_input`，用户在任务中心
  回一句，`resume()` 从断点继续。**已花掉的步数不重跑**，这是与"打回重问"的本质差别。
- **H3 完成通知与窗口对齐。** 任务中心窗口须覆盖审批队列最长等待（4 天）。

## 5. 交接后的送达方式（10 秒阈值下的关键设计）

阈值 45s 时交接是异常路径，跳去任务中心可以接受。**10 秒阈值下它是常态路径**，
再让用户换一页看结果就是把过半查询的体验判了死刑。

因此交接后的默认行为是**原地接管，不是跳转**：

1. 主请求返回回执，查询页把当前这条问句就地切成"执行中"卡片，保留问题原文与数据源；
2. 页面按 thread_id 轮询 `/api/tasks`（或单条任务接口），拿到 final 就**在原位置**
   渲染出完整结果，与同步返回的结果一模一样；
3. 用户中途离开或刷新，任务照跑不误，任务中心里那条线程是同一条；
4. 只有在任务停在需要人动手的档（等审批 / 等补充 / 等运维）时，卡片才给出明确的
   下一步入口 —— 那句话直接取 `_NEXT_ACTOR`，不另写一份。

「创建任务」（A-1）是唯一例外：那是用户显式声明"我不等了"，回执即可。

## 6. 容量与影响（必须一起做的配套）

按 `docs/test-report-agent-soak.md` 实测 p50 = 9.6s：**10 秒阈值意味着约一半的
模型链路请求会交接到后台**。叠加应答缓存 73% 的命中率（缓存命中不进链路），
折算到总流量约 13%~15%。配套如下：

| 项 | 现状 | 调整 |
|---|---|---|
| 后台池 | `ThreadPoolExecutor(max_workers=8)`，进程内 | 提到 16 并设**每账号在跑上限**（建议 3），满则拒绝并说明理由，不排队 —— 排队会让回执里的"正在执行"变成谎话 |
| 池满时的行为 | 无处理 | 明确降级：不交接、继续同步等，等到 nginx 边界为止（宁可慢，不可丢） |
| 配额 | 按次计，交接不改变计数 | 不变。交接是送达方式的变化，不是新的一次消费 |
| 审计量 | 每线程 2 条（起、终） | G2 每节点一条后按 6 步算约 8 条，日十万级下要复核保留期与索引 |
| nginx `/api/ask` 20 r/min | 不变 | 交接后主请求早退，实际占用连接更短，限流无需放宽 |

## 7. 分期落地

| 阶段 | 目标日期 | 内容 | 验收 | 状态 |
|---|---|---|---|---|
| 一 · 前置 | 2026-09-19 | G1 前端识别回执 + §5 原地接管；G4 窗口对齐。**本阶段不动阈值** | 构造一条 >10s 的查询（临时改 dev 配置），页面出执行中卡片并在原位接管结果 | ✅ 2026-09-13 |
| 二 · 切阈值 | 2026-09-23 | 生产 `async_after_ms` 45000 → 10000；§6 池与每账号上限；池满降级 | 灰度一天：交接率、池水位、504 数、任务中心回访率四项达标 | ✅ 2026-09-13（与阶段一同批上线，前端已能接住） |
| 三 · 全入口 | 2026-09-30 | §2.0 第 2 条：`/api/resume` 等全部执行入口接 `run_or_detach`；节点边界交接；A-1~A-7 提前交接；G2 进度 | 续跑一条长线程不再 504；多步任务在任务中心看得到"第 k 步 / 当前工具" | ✅ 2026-09-13（A-3 慢源标记、A-4 池水位除外，见下） |
| 四 · 韧性 | 2026-10-15 | R1 优雅退出 + R2 启动自愈 + R3 取消 | 滚动更新期间发起 20 条长任务，全部自愈或如实转等运维，零静默丢失 | 未开始 |
| 五 · 介入 | 2026-10-31 | H1 审批后代跑 + H2 图内 interrupt | 补充条件后不重跑已完成步数（step_count 连续增长而非归零） | 未开始 |

阶段三里两条**有意没做**，不是漏了：

- **A-3 慢源标记**：现在没有任何一个源被标过慢，加了也是空配置项。等真有源
  稳定跑长再加，那时才知道该按什么标。
- **A-4 池水位提前交接**：池满已经有明确处置（不交接、同步跑到底）。再加一条
  "快满了就提前交接"会让同一件事有两套判定，而两套判定的分歧只会在高水位
  —— 也就是最不该出意外的时候 —— 才暴露。

**阶段一与阶段二必须分开、且顺序不可换。** 先切阈值再修前端，等于一次性把过半
请求送进一个渲染不出来的分支。

## 8. 明确不做

- 不建任务表。任务概念落在审计流水与检查点上，这是现有口径，多一份存储就多一次漂移。
- 不引入外部队列（Celery/RQ）。当前量级下进程内有界池 + 共享检查点够用；
  到日访问十万级再评估。
- 不给任务"预计剩余时间"。给不出可信估计的数字，比不给更糟。
