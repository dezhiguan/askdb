DESIGN REVIEW · 2026-09-27

当前库先答。答不全再补源。

提问继续只带当前空间。选源发生在执行 SQL 之前，用现有的 Schema 召回完成，不交给规划模型凭数据源名字去猜，页面上也不做勾选。两个库的数要出现在同一个答案里，必须事先登记聚合契约。

待审核 不改查询页选择器 沿用编排图 aggregate_only
01

结论

线上已经有十几个数据源。每次提问都去扫全部库，简单计数也会变慢，也更容易把同名表查错库。

默认只查当前空间。当前库的召回盖不住这个问题时，才在这个用户有权查的源里补，而且只补真命中了不同表的源。

这一版定下的事

  • 查询页保持单选，顶栏「当前空间」仍是默认库
  • 选源用 search_schema，不用 Supervisor 自由挑名字
  • 合并走现成的 JoinContract，缺契约不合成一个数
  • 一条 SQL 仍然不能跨库，R-06 保持原样
02

三条出路

同一次提问只走其中一条。判定在进单智能体或编排图之前完成。

PATH A · 单源

当前库能答

召回命中了表，而且不是盲选。问题留在现在的查询智能体里。

  1. 只对当前空间做 search_schema
  2. 命中表，blind 为假
  3. 走现有单智能体，不读其他库
PATH B · 跨源

要补，而且允许合并

别的已授权源命中了当前库没有的表，并且每一对都有聚合契约。

  1. 对其余已授权、已开放表的源再召回
  2. 留下命中表与当前库不重复的源
  3. 最多 max_workers 个，现在是 3
  4. 交给 run_multi_agent
PATH C · 不合并

要补，但没有契约

相关库存在，部署配置里没有这一对的 JoinContract。

  1. 当前库自己能答：答当前库，并写明另一个库未参与汇总
  2. 当前库答不了：P12 拒绝，写出是哪一对源
  3. 不把两边的行拼成一个数
03

选源规则

第一段只看当前空间。第二段才看其他源。第二段不是每次都跑。

01
收窄候选候选只包括当前用户已经有权查询、并且开放了表的源。无权的源不进召回。
02
先召回当前库复用 search_schema。看命中表、blind、coverage_gaps。这一步不执行 SQL。
03
决定要不要扩当前库已覆盖，停在 PATH A。下面任一成立才进入第二段：召回是盲选、存在覆盖缺口，或问题里有「分别」「对比」「跨数据源」。
04
再召回其他源只保留真命中了表、且这些表不在当前库命中集合里的源。召回分数靠后的丢掉。加上当前库，总数不超过 max_workers。
05
核对契约选出的源超过一个时，调用现有的 approved_contracts。每一对都要有 aggregate_only: true 的契约，否则走 PATH C。

「分别」「对比」只用来决定要不要去看其他库，不用来决定把哪两个库合在一起。合并不合，只看契约。

04

怎么执行

跨源不新开一条 SQL 通道。选源结束之后，走已经接好的编排图。

环节这一版怎么用现有位置
入口 请求仍只带当前空间的 source。服务端自己算出这次要查的源列表，再传给 run_ask 的 source_configs。 server.py 的 /api/ask
路由 算出的源多于一个，并且契约齐全，就进编排。一个源保持单智能体。 decide_route 已有 source_count > 1
规划 Supervisor 收到的是「源 id + 这次命中的表名」，不是一串光秃秃的名字。source_id 必须落在这批源里。 supervisor_graph._supervisor
越权 模型写出名单外的源 id，config_for 直接拒绝。 MultiAgentDeps.config_for
取数 每个 Query Worker 只用该源已经收窄过的配置跑 search_schema 和 execute_sql。 query_worker_agent
汇总 合成器只拿各源的聚合结果和契约写答案。原始行留在各自的库里。 JoinContract、federation.py
05

合并不了的时候

缺契约、开关关闭、或当前库与另一个库撞车，都按下面这张表收口。页面把原因写出来。

情况给用户的结果
当前库能答，另一个库也有相关表，但没有这一对契约 答案来自当前库。文案写明另一个库的名称，以及它未参与汇总。
当前库是盲选或覆盖缺口，问题必须靠另一个库，而这一对没有契约 拒绝。沿用 P12，正文写出两个源的名称。
allow_cross_source 仍是 false 与上一行相同的收口：能单源答就单源答并说明；不能答就拒绝。不因为用户没勾选而静默查第二个库。
召回命中超过 3 个源 保留当前库，再按命中取满 max_workers。没进名单的源不执行 SQL。
06

配置

config/public.yaml 与 config/askdb.yaml 一起改。源 id 用运行时数据源 id。没有写好的源对，开关打开也不会合并它们。

multi_agent:
  allow_cross_source: true
  join_contracts:
    - contract_id: orders_events_day
      left_source: src_orders
      right_source: src_events
      join_keys: [date]
      grain: day
      aggregate_only: true
      timezone: Asia/Shanghai

契约

  • 三个源一起出现，就要三对契约
  • aggregate_only 保持 true，代码只认这种契约
  • 新的源对要改配置再发布。这一版不接人工审批队列

预算

跨源至少是两个完整 Worker。现有 cost_cap_tokens: 30000 会在合成前截断。跨源运行单独提高上限。

具体提高到多少，这一页先不定，审核时补一个数字。

07

页面

选择器、顶栏、口径页、信任侧栏、数据源管理都继续只认一个当前空间。跨源是这一次提问算出来的范围。

查询页

  • 不增加多选，请求仍提交当前 source
  • 单源答案的版式不变
  • 跨源答案上方写「这次查了 A、B」
  • 若走了 PATH C 的单源降级，同一位置写明未参与的库
  • 示例问题和最近查询仍只跟当前空间

结果与追踪

  • 协作详情里的 source_id 显示成数据源名称
  • Evidence 账本按源展开，SQL 分块，每条 SQL 标自己的库
  • 执行追踪右栏的「数据源」列出这次各 Worker 的源
  • 追踪列表的筛选仍按单个源
08

选错怎么拦

自动选源会错。这一版把错挡在执行之前，避免「SQL 跑通了、库却是错的」。

错法拦法
两个库都有「订单」，凭名字挑了一个能查出数的库 当前库已经命中且不是盲选时，不扩源。不把源名字交给规划模型自由选择。
当前库够用，仍把另一个擦边的库拉进来合成 第二段只收「当前库没有的表」。没有新表的源不执行。
该查的库没被召回，答案缺了一半还不说 盲选和 coverage_gaps 会触发第二段。第二段仍不够、又不能合并时，拒绝或明示降级，不把残缺结果当成完整答案。
模型在计划里写了一个这次没授权的源 config_for 拒绝。Worker 的配置在进图之前就按用户权限收窄。
09

保持不动

这些边界这一版不放宽。

  • R-06：一条 SQL 里的 其他库.schema.表 继续拒绝
  • 每个 Worker 只使用该源自己的连接、白名单、脱敏和租户条件
  • 应答缓存继续跳过多源请求
  • 续跑继续按每个源的权限指纹复核，指纹变了就 RESUME_BLOCKED
  • 直查 /api/sql 仍是一个源
  • 单智能体仍是一个连接。跨源只出现在编排图里
