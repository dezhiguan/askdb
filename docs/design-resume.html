1现状与场景

1.1机制全在，但一次都没用上

askdb 已经挂了 SqliteSaver，每次调用写 9.3 个快照、97 KB。 但代码里只有 get_state_history() 一处读取 —— 没有任何一处 invoke(None, cfg)，也就是从不恢复。

而且 thread_id 每次换新 当前每次问答都用一个全新的 trace_id 作 thread_id， 等于每次都是一次性 thread。"未完成的任务"这个概念根本不存在， 自然也无从恢复。设计文档 §5 明确写了「而非在线断点续跑」—— 是有意识的取舍，不是遗漏。

1.2什么情况下值得续跑

单步问答约 5 秒，重问比恢复省事，续跑没有价值。真正值钱的是下面两类：

场景典型耗时失败重来的代价优先级
多步问答（planner 开启） P95 18.6 s 最多 3 步 × 3 次生成 = 9 次模型调用全部作废 中
评测批跑 20–30 min 58 题 × 6 组 = 348 次调用。本项目已真实发生两次：一次配额中途触顶致 23 题作废，一次因判定器缺陷被中途终止 高

本设计先做多步问答（形态简单、界面可见），评测批跑的续跑作为 R3 阶段。

2界面原型

点上方按钮切换四个状态。这是提问页在续跑场景下的形态。

状态
askdb可信数据问答
org_id = 65 执行中
界面上的三个关键决定 ① 恢复入口不是列表，是横幅。askdb 无账号体系，列出"所有未完成任务" 等于给任何人一个枚举接口（见 §4.2）。所以只在本浏览器留有该 trace_id 时 才提示。
② 已完成的步骤要显示成"跳过"而不是隐藏。让人看清恢复省掉了什么、 从哪一步接上 —— 这本身就是续跑价值的证据。
③ 成本要分两段显示。中断前已花的钱不会退，必须让人看到 "本次续跑新增"与"累计合计"，而不是只显示后者。

3机制设计

3.1三处改动

#改动说明
1thread_id 与 trace_id 解耦 现在两者相同。改为：thread_id 标识一个任务，可跨多次 invoke；trace_id 仍标识一次执行，用于审计。 恢复时 thread 不变、trace 新开一条，审计里因此能看出"这是第 2 次执行同一任务"
2任务完成标记 状态里加 finished: bool。get_state(cfg).next 非空 即为未完成 —— 但显式标记比推断可靠，也便于区分"未完成"与"已完成但还有边"
3恢复入口 POST /api/resume，体内带 thread_id。 服务端执行 app.invoke(None, cfg)

3.2恢复的核心只有一行

# 不给新输入，从最后一个检查点的 next 节点继续
out = app.invoke(None, {"configurable": {"thread_id": tid, "deps": deps}})

已实测验证：三步任务在第 2 步被杀进程，重启后读到 已完成 ['step1']，下一步 ('step2',)，续跑后 step1 未重跑。

4安全约束

4.1恢复会重置成本护栏 —— 这是个后门

立项前实测确认 R-17 累计成本上限的判定是 used = d.tracer.tok_in + d.tracer.tok_out， 而 Tracer 是进程内对象，经 configurable 传入， 不在检查点状态里。 恢复时会新建一个 Tracer —— used 归零，R-17 形同虚设。

后果很具体：反复"中断 → 恢复"即可绕过单次问答的 token 上限，无限花钱。 这与"每日配额靠审计条数、日志不持久化就归零"是同一类错误 —— 护栏的计数器必须和护栏本身一样持久。

护栏计数位置恢复后处理
R-14 重试上限attempt（状态内）正确继承无需改动
R-16 步数上限step_no（状态内）正确继承无需改动
R-17 成本上限Tracer（进程内）被重置把累计 token 移入状态，Tracer 恢复时从状态回种
每日配额审计日志条数正确已挂持久卷；但恢复应另计一次调用，不能白嫖

这条是本设计的前置条件：R-17 不改成状态内计数，续跑功能不得上线。

4.2任务不可枚举

askdb 无账号体系（§1.1：数据库连接本身即权限边界）。因此：

  • 不提供"未完成任务列表"接口 —— 那等于给任何人一个枚举入口， 与上一份《回放接口设计》拒绝做列表页是同一条理由
  • 恢复入口只接受调用方自己持有的 thread_id， 由浏览器本地保存（localStorage）
  • thread_id 命中与未命中同返回 404，不区分"不存在"与"存在但非你的"
  • /api/resume 与 /api/ask 共用同一档限流 —— 它同样会花钱，没有理由更宽松

5幂等边界

恢复的粒度是节点，不是节点内部。断点所在的那个节点会整个重跑。 因此必须逐节点确认重跑是否安全：

节点重跑安全说明
retrieve / guard / dry_run安全纯计算或只读，无副作用
execute安全askdb 只执行 SELECT（R-02 保证），重跑不改变数据
plan / generate / assess花钱会再调一次模型。不是正确性问题，是成本问题 —— 由 §4.1 修好后的 R-17 兜住
finalize注意写审计。恢复应写新的一条（新 trace_id）而非覆盖，两条通过同一 thread_id 关联
askdb 在这件事上占了便宜 通用 Agent 做续跑最难的是副作用回滚（邮件已发、订单已建）。 askdb 的执行节点只读，R-02 从语句类型上就杜绝了写操作 —— 重跑最坏只是多花一次模型调用的钱。这是"只读"这条约束的额外红利。

7.1两项已定夺事项（V1.1）

① 续跑计入每日配额

决定：计入，按一次独立调用计。理由与 §4.1 同源 —— 不计入就等于开了一条绕过配额的路径：中断一次、恢复一次， 两次模型调用只扣一次额度；反复中断即可无限刷。

界面上必须说明这一点（原型状态③的横幅已写： 「本次续跑另计一次每日配额」）—— 否则用户会以为续跑是"补完上次"因而免费。

与「跳过的节点不花钱」不矛盾 续跑确实跳过了已完成节点、没有重复调用模型，省下的是 token 成本； 但配额限制的是调用次数，是防滥用的闸门，不是成本的度量。 两者目的不同，不该互相抵扣。

② 不做自动恢复

决定：只在页面上由人点击触发。三条理由：

  • 自动重试会放大故障。中断的常见原因是模型超时、配额耗尽、 数据源不可用 —— 这些情况下自动恢复只会立刻再失败一次， 并把故障期间的请求量翻倍。这与 §5.1 的判断一致： 连接不可达时重试纯属浪费。
  • 成本必须由人确认。续跑要花钱、要占配额， 界面已明确显示"中断前已花 ¥0.0021 不会退"与"本次另计一次配额"， 让人在知情下决定。
  • 失败诚实优先于自愈。设计文档 §4.5 的原则是"不做静默降级"—— 自动恢复是另一种形式的静默：用户不知道系统替他重跑过。

后续若确有需要，可考虑「仅对明确可重试的中断原因自动恢复一次」 （如进程重启，排除模型故障与配额耗尽），但那需要先有中断原因的分类， 本版不做。
