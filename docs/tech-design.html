1概述

1.1定位

askdb 是一个把自然语言问题转换为受控 SQL 并安全执行的独立工具。它的核心命题不是"让模型会写 SQL"，而是在模型不可靠的前提下，让整条执行链路可靠。

产品形态为贴着数据源运行的本地/内网工具，不设账号体系 —— 数据库连接本身即权限边界。同时对外暴露 MCP 接口，可被其他 Agent 作为工具调用。

1.2目标与非目标

目标

  • 自然语言问题 → 可执行、可核对的 SQL
  • 危险操作在执行前被零成本拦截
  • 多租户场景下不发生跨租户数据可见
  • 输出必须附带 SQL，支持人工自验
  • 每次调用的 token 与耗时可归因到链路步骤
  • 准确率提升可通过消融实验逐项归因

非目标

  • 不做账号/会话/权限体系
  • 不做多轮对话上下文
  • 不做图表生成与报表编排
  • 不做数据写入与运维操作
  • 不追求覆盖任意复杂分析型查询
  • 不替代 BI 与数据分析岗位
前提认知 NL2SQL 在真实企业库（表命名不规范、存在历史遗留表、业务口径隐含于人）的执行准确率通常落在 40–60% 区间，与学术基准上的 85%+ 不具可比性。本设计的一切护栏、口径层与评测机制， 都是围绕"承认模型会错"这一前提展开，而非试图消除错误。

1.3术语

术语含义
产出物 / Artifact模型生成的、将被真实执行的内容。本项目中特指 SQL 语句
静态校验在 AST 层完成的纯代码判定，不调用模型、不访问数据库，成本为零
强制改写在 AST 上追加不可被生成内容覆盖的约束（LIMIT、租户谓词）
语义层 / 口径业务指标的机器可读定义，数据库 schema 中不存在的知识
执行准确率生成 SQL 的执行结果集与标准答案结果集一致的比例
盲测集实现阶段全程不可见、仅在验收时一次性运行的评测子集

2总体架构

2.1链路总览

用户问题 │ ├─▶ [1] Schema 召回 向量检索相关表/字段/口径，仅注入命中项 │ ├─▶ [2] 规划 / 重规划 判定单步可答或需多步；多步时给出本步目标 │ ▲ │ └──────────────────────────────────┐ ├─▶ [3] SQL 生成 结构化输出，强制 JSON schema │ │ │ ├─▶ [4] 静态校验 AST 判定 + 强制改写 · 零 token 成本 │ │ └── 不通过 ──▶ [7] 反思重试 ──▶ 回到 [3] │ │ │ ├─▶ [5] EXPLAIN 干跑 预估扫描行数，超阈值打回 │ │ │ ├─▶ [6] 只读执行 独立只读账号 + 超时 + 行数上限 │ │ └── 执行报错 ──▶ [7] 反思重试 ──▶ 回到 [3] │ │ │ ├─▶ [8] 结果评估 本步结果是否足以作答？ │ │ └── 不足 ─── 携带中间结果摘要，重规划 ───────┘ │ （受 R-16 步数上限 / R-17 累计成本上限约束） │ └─▶ [9] 结果与溯源 最终结果 + 全部轮次 SQL + 数据时间 + 步数
设计原则 第 4 步永远是代码判定，不是模型判定。让模型审查自己的产出等同于没有护栏。 静态校验不引入任何 LLM 调用，这是它能够"零成本拦截"的前提，也是整条链路成本可控的关键。

3数据接入设计

数据接入分三层。工程难度集中在第二、三层，而多数同类实现只处理了第一层。

层内容难度失败后果
①连接层：只读账号、连接池、数据库级限制低无法连接，问题显性
②Schema 层：表白名单、字段语义注释、向量召回高准确率塌方，且不易察觉
③语义层：业务指标口径定义最高答案看似合理但口径错

3.1连接层

护栏优先做在数据库侧而非应用侧。应用层校验可能被绕过，数据库权限不会。

CREATE ROLE askdb_ro LOGIN PASSWORD '***';

GRANT CONNECT ON DATABASE ragforge TO askdb_ro;
GRANT USAGE   ON SCHEMA public   TO askdb_ro;

-- 逐表授权，禁止 ALL TABLES
GRANT SELECT ON documents, knowledge_bases, orgs, model_usage TO askdb_ro;

-- 数据库级硬护栏
ALTER ROLE askdb_ro SET default_transaction_read_only = on;
ALTER ROLE askdb_ro SET statement_timeout = '8s';
ALTER ROLE askdb_ro SET idle_in_transaction_session_timeout = '10s';
ALTER ROLE askdb_ro CONNECTION LIMIT 3;

连接自检

启动与「测试连接」时执行六项自检，任一项不通过则拒绝进入可用状态：

#检查项判定方式
1网络可达与认证建立连接并记录 RTT
2账号为只读SHOW default_transaction_read_only = on
3语句超时已设置SHOW statement_timeout ≤ 配置值
4连接数上限已设置查询 pg_roles.rolconnlimit > 0
5授权表集合information_schema.role_table_grants 与白名单比对
6写操作实探发起一条 INSERT，必须被拒绝；成功则判定失败
第 6 项的意义 前五项检查的是"配置声称什么"，第六项检查的是"实际拦不拦"。 配置漂移、角色继承、连接串指向错误库等情况，只有实探能发现。

3.2Schema 层

3.2.1 表白名单

禁止全库注入。白名单同时是安全边界与准确率边界 —— 无关表会干扰模型选表。经验规模为 10–20 张。排除标准：

  • 超大表（如切片正文表，亿级行）—— 任何聚合都是风险
  • 无业务语义表（迁移记录、临时表、历史遗留表）
  • 含敏感字段且无脱敏方案的表

3.2.2 字段语义注释

生产库的 COMMENT 覆盖率通常极低，而字段名（如 t_doc_stat、kb_cnt）不具自解释性。因此维护一份独立的 schema 增强文件，与数据库解耦。

tables:
  - name: documents
    desc: 知识库文档主表，一行 = 一个上传的文件
    aliases: [文档, 文件, 资料]
    columns:
      status:
        type: varchar
        desc: 处理状态
        enum: [PENDING, PROCESSING, COMPLETED, FAILED]
        note: 「文档数」口径为 COMPLETED 的数量，非全部行数
      org_id:
        type: bigint
        desc: 组织 ID
        tenant: true          # 租户隔离列，触发强制改写
      updated_at:
        type: timestamptz
        desc: 最后状态变更时间（非内容更新时间）
关键判断 这份文件的质量约等于项目的准确率。它的边际收益高于更换更大的模型， 且成本是一次性的。实施时应把主要人力投在此处，而非提示词调优。

3.2.3 向量召回

每张表构造一段检索文档：表名 + 描述 + 别名 + 字段清单（名/类型/说明/枚举），向量化后建立索引。提问时召回 Top-K（默认 3，上限 5）表，仅将命中表的 schema 注入提示词。

token 预算：单次注入控制在 1 500 tokens 以内。超出时按相似度截断并记录告警 —— 静默截断会造成不可解释的准确率下降。

3.3语义层

业务口径是 schema 中不存在、模型无法推断的知识。未显式定义时，模型只能猜测，且猜错时输出仍然"看起来合理"。

metrics:
  - name: 文档数
    aliases: [文档数量, 已入库文档, 完成数]
    expr: "COUNT(*) FILTER (WHERE status = 'COMPLETED')"
    scope: [documents]
    owner: 平台组

  - name: 卡住的文档
    aliases: [卡住, 处理中不动, 堆积的文档]
    predicate: "status = 'PROCESSING' AND updated_at < now() - interval '1 hour'"
    scope: [documents]
    owner: 平台组

召回逻辑：问题文本命中 name 或 aliases 时，将口径定义随 schema 一并注入，并在提示词中约束"涉及该指标必须使用给定表达式，不得自行构造"。

4护栏设计

本章是项目核心。护栏分为静态校验（AST 层，零成本）、强制改写（AST 层，不可绕过）、执行限制（数据库层，兜底）三类。

4.1规则清单

编号规则类型阻断说明
R-01单语句限制静态校验是解析结果必须恰好 1 条语句，防多语句夹带
R-02语句类型白名单静态校验是仅允许 SELECT 与 WITH…SELECT
R-03表白名单静态校验是含子查询、CTE、JOIN 中出现的全部表引用
R-04字段真实性静态校验是比对 schema，拦截幻觉字段
R-05禁止 SELECT *静态校验否改写为显式列，控制列暴露面
R-06禁止跨 schema / 跨库引用静态校验是拦截 other_schema.tbl、dblink
R-07危险函数黑名单静态校验是pg_read_file / lo_import / dblink / pg_sleep 等
R-08笛卡尔积检测静态校验是JOIN 缺少 ON 条件或恒真条件
R-09强制 LIMIT 注入强制改写—无 LIMIT 则追加；已有且超上限则下调
R-10强制租户谓词注入强制改写—见 4.4，含子查询与 CTE 的每一层
R-11扫描行数阈值干跑是EXPLAIN 预估行数超阈值则打回
R-12语句超时执行限制是数据库会话级，默认 8s
R-13结果行上限执行限制是默认 1 000 行，超出截断并标注
R-14重试次数上限链路控制是默认 2 次，防无限循环与成本失控
R-15中间结果规模上限链路控制是多步规划中，上一步结果超过 50 行则拒绝作为下一步输入
R-16总步数上限链路控制是单次问答最多 3 步，达上限即收敛作答
R-17累计成本上限链路控制是单次问答全部步骤与重试的 token 总和封顶
R-15～R-17 的必要性 多步规划把单次问答的成本与不确定性从"有界"变成"可增长"。 这三条是把它重新变回有界的机制 —— 缺任何一条，一次提问都可能演变为不收敛的循环。

4.2静态校验实现要点

全部判定基于 sqlglot 解析出的 AST，不做任何字符串匹配。理由：注释、大小写、编码变形、Unicode 同形字都能绕过字符串匹配，但解析器会先行规范化。

表引用收集必须遍历完整 AST，覆盖：FROM / JOIN / 子查询 / CTE / IN (SELECT …) / EXISTS / LATERAL / UNION 各分支。漏掉任一分支即构成绕过路径。

4.3强制改写

改写在 AST 上完成后重新生成 SQL，模型无法通过任何提示词手段覆盖。改写结果对用户可见并高亮标注，保证透明性。

-- 模型产出
SELECT file_name, status FROM documents WHERE status = 'PROCESSING';

-- 强制改写后（实际执行）
SELECT file_name, status FROM documents
WHERE status = 'PROCESSING'
  AND org_id = 65          -- R-10
LIMIT 1000;                    -- R-09

4.4租户隔离（双层）

重要 仅依赖应用层 AST 改写不足以保证多租户隔离。需覆盖子查询、CTE、UNION、 多层 JOIN、视图、LATERAL 等全部分支，任一分支遗漏即构成越权路径。 因此隔离必须下沉至数据库层。

第一层：应用层 AST 改写（R-10）

对每一层查询块中出现的、带 tenant: true 标记列的表，追加租户谓词。无法确定租户归属的查询直接拒绝执行，而非放行。

第二层：数据库行级安全（RLS）

ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY org_isolation ON documents
  FOR SELECT TO askdb_ro
  USING (org_id = current_setting('app.org_id')::bigint);

连接取出后、执行前注入会话变量：

SET LOCAL app.org_id = '65';

效果：即使生成的 SQL 中完全不含租户条件，数据库也只返回该租户的行，SQL 层面无法绕过。

RLS 使用约束 ① askdb_ro 必须为普通角色 —— superuser 与具备 BYPASSRLS 的角色会跳过策略； ② RLS 谓词参与查询计划，大表上需确保租户列已建索引，否则退化为全表扫描； ③ 视图默认以定义者权限执行，需显式使用 security_invoker（PG 15+）否则策略被绕过。

4.5反思重试

触发条件：静态校验未通过（R-01～R-08）或执行报错。将真实错误信息与失败 SQL 一并回灌模型重新生成，同时按错误类型补充召回（例如字段不存在时，扩大 schema 召回范围）。

重试次数上限 2 次（R-14）。达到上限后返回失败并附完整判定链路，不做静默降级 —— 返回一个"差不多的答案"比返回失败更危险。

5状态机设计

使用 LangGraph 建模。选择状态机而非线性链的原因：存在条件分支（校验失败回边）与重试计数，且需支持检查点以便失败复现。

状态结构

class AskState(TypedDict):
    question:   str
    ctx:        QueryContext      # org_id / trace_id / 发起方
    tables:     list[TableSpec]   # [1] 召回结果
    metrics:    list[Metric]      # [1] 命中的口径
    plan:       str               # [2] 本步目标
    multi_step: bool              # [2] 规划判定：是否需要多步
    sql_raw:    str               # [3] 模型原始产出
    sql_final:  str               # [4] 强制改写后
    guard:      GuardResult       # 命中规则、改写项、拒绝原因
    explain:    ExplainResult     # [5] 预估行数与代价
    rows:       list[dict]        # [6] 本步结果
    error:      str | None
    attempt:    int               # [7] 本步重试计数，上限 2（R-14）

    # ---- 多步规划（V1.1 新增）----
    step_no:    int               # 当前第几步，上限 3（R-16）
    steps_done: list[SubStep]     # 每步的目标 / SQL / 结果摘要
    carry:      dict              # 下传给下一步的字面量（受 R-15 约束）
    enough:     bool              # [8] 结果评估：是否足以作答
    cost_acc:   CostAcc           # 累计 token 与成本（R-17）

    trace:      list[StepTrace]   # 步骤级耗时与 token

5.3多步查询规划

首要设计原则 能用一条 SQL 表达的依赖，一律交给 SQL，不走多步。 大量看似"多跳"的问题（如"哪个知识库失败率最高，它的失败文档是什么类型"） 用 CTE 或窗口函数单条即可完成，且更快、更便宜、更准。 多步规划是兜底路径，不是默认路径 —— 滥用会同时抬高成本、延迟与错误率。

5.3.1 触发条件

plan 节点仅在满足以下情形之一时判定 multi_step = true：

情形说明示例
探索型需要先观察数据的实际取值分布，才能确定筛选条件"看看处理状态都有哪些取值，再统计非正常状态的分布"
结果驱动分支第一步的结果决定第二步查哪张表或用哪套口径"最近异常的是哪个模块，把它对应的明细拉出来"
超出 SQL 表达能力中间需要 LLM 做语义判断，SQL 无法表达"找出命名不规范的知识库，统计它们的文档量"

不满足上述任一情形时，即便问题表面包含多个子问题，也应生成单条 SQL。plan 节点的提示词中须显式给出上述判据与反例。

5.3.2 中间结果下传

中间结果不以结果集形式回灌提示词（体量不可控且浪费 token），而是提取为字面量注入下一步：

-- 第 1 步：找出失败率最高的 3 个知识库
SELECT kb_id, ... FROM documents WHERE org_id = 65
GROUP BY kb_id ORDER BY fail_rate DESC LIMIT 3;
-- 结果：kb_id = 12, 7, 31

-- carry = {"kb_ids": [12, 7, 31]}   ← 仅下传标识列，不下传整行

-- 第 2 步：由规划节点生成新目标，字面量注入
SELECT kb_id, file_type, COUNT(*) FROM documents
WHERE status = 'FAILED' AND kb_id IN (12, 7, 31)
  AND org_id = 65
GROUP BY kb_id, file_type LIMIT 1000;

下传内容受 R-15 约束：中间结果超过 50 行时拒绝下传，转为提示用户细化问题。原因是字面量列表过长会导致提示词膨胀、SQL 长度失控，且往往意味着第一步的筛选本身有问题。

5.3.3 每步独立过全量护栏

不得放松 第 2、3 步生成的 SQL 必须完整通过 R-01～R-13 全部规则， 包括表白名单、字段真实性、租户谓词强制注入。 不存在"因为是后续步骤所以已被信任"的路径 —— 每一步都是独立的不可信产出。

5.3.4 重试与步数的计数关系

两个计数器相互独立：

  • attempt —— 按步重置。第 2 步失败重试，不影响也不重跑第 1 步
  • step_no —— 全局递增，上限 3（R-16）

因此单次问答的最坏情况为 3 步 × 3 次生成 = 9 次模型调用，由 R-17 累计成本上限做最终兜底。

5.3.5 收敛与降级

触及 R-16 或 R-17 上限时，不静默返回部分结果，而是：基于已完成步骤作答，并在输出中明确标注「因步数/成本上限提前收敛，结论可能不完整」，同时附全部轮次的 SQL 供人工继续。

6.4防自证机制

自建评测集存在"出题人即答题人"的固有质疑，须以机制而非声明应对：

  1. 顺序锁定 —— 黄金集在 guard.py 实现开始前完成并 git 打标冻结；实施期间不得因"拦不住"而删改题目
    V1.2 如实修订 本条在实施中未被严格执行。黄金集虽在 guard.py 之前完成， 但当时未打标签，冻结标签 golden-frozen-v1 是在实施结束后（2026-08-12）才补上的。 期间黄金集被修改过一次 —— 部分标准答案用了裸 COUNT(*)， 与 metrics.yaml 中「文档数 = COMPLETED 数」的口径冲突， 即标准答案本身是错的，修正后模型侧准确率上升。改动本身正确， 但因缺少冻结点，这一判断无法由第三方独立复核。 改动记录见 git log evals/golden.py。后续项目须在实现开始前打标。
  2. 盲测集隔离 —— 15 题在实施全程不可见，仅在 P3 验收时一次性运行。盲测集成绩为最终成绩
  3. 对照组同题 —— 各消融组运行完全相同的题目，仅改变配置
  4. 失败样本留存 —— 全部失败样本连同检查点入库，报告中公开失败分类分布，不做筛选

场景结论依据

10.1已识别风险

等级风险缓解措施
高AST 改写遗漏分支导致越权。子查询、CTE、UNION、视图任一分支未覆盖即构成漏洞数据库 RLS 兜底（4.4）；针对每类语法结构编写专项用例

-- ============ 1. 只读角色 ============
CREATE ROLE askdb_ro LOGIN PASSWORD '***';

GRANT CONNECT ON DATABASE ragforge TO askdb_ro;
GRANT USAGE   ON SCHEMA public   TO askdb_ro;

-- 逐表授权，禁止 ALL TABLES
GRANT SELECT ON documents, knowledge_bases, orgs, model_usage TO askdb_ro;

-- ============ 2. 数据库级硬护栏 ============
ALTER ROLE askdb_ro SET default_transaction_read_only = on;
ALTER ROLE askdb_ro SET statement_timeout = '8s';
ALTER ROLE askdb_ro SET idle_in_transaction_session_timeout = '10s';
ALTER ROLE askdb_ro CONNECTION LIMIT 3;

-- ============ 3. 行级安全（每张含租户列的表都要做）============
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY org_isolation ON documents
  FOR SELECT TO askdb_ro
  USING (org_id = current_setting('app.org_id', true)::bigint);

-- 租户列索引，避免 RLS 谓词导致全表扫描
CREATE INDEX IF NOT EXISTS idx_documents_org_status
  ON documents (org_id, status, updated_at);
