00结论先行

三条判断决定了整份方案的形状。它们都来自代码与生产 trace，不是从通用做法推的。

成本来源

输出 + 轮数

前缀缓存已隐式命中 86–91%，命中部分按 1/8 计价。 “提示词太长”不是成本来源 —— 输出 token 占单链路成本约一半。

语义缓存该缓存什么

答案→SQL

连的是生产库：答案有保质期，SQL 没有。命中后重跑一条 15ms 的 SQL， 比返回一份十分钟前的数字既便宜又正确。

首字延迟

全链路→SQL 跑完那刻

结果表在收敛轮之前就已经在 last_exec 里， 现在却要等模型写完结论才一起送达。先推结果表：零成本、零调用、零判定风险。

02动手之前必须先修的六个缺口

这六条不是优化，是先把账和闸修对。否则后面每一层缓存的收益都无法证明 —— 而其中 D-6 更要紧：不修它，后面三层缓存对最贵的那批流量根本不生效。

D-1前端主路径绕过了每 IP 成本闸

deploy/nginx-askdb.conf 里 location = /api/ask 是精确匹配， 挂着 20r/m 的 askdb_ask 档。而前端实际走的是 askQuestionStream → /api/ask/stream，它落进 location /， 只吃 server 块那条 30r/s。

限流注释里写的“挡的是一个人把全站额度花光”，在主路径上不成立。这是当前唯一一个任何人都能持续烧钱的敞口。

修法 新增 location = /api/ask/stream，同挂 askdb_ask；proxy_read_timeout 60s、proxy_buffering off（30s 读超时会在一次长 decide 上把流掐断）。

D-2应答缓存 key 缺三个维度，配置收紧后十分钟内仍返回旧口径

qcache.make_key 只带 question / source_id / org_id / role。 源的白名单、脱敏列、护栏参数改了之后 key 不变 —— 旧答案（含旧脱敏口径）继续被返回最长 10 分钟。

这不只是新鲜度问题：脱敏那一维是安全口径，改配置的人会认为改完即生效。

修法 key 并入 cfg 指纹（表白名单 + 脱敏列 + guard 版本）。vectors._fingerprint 已有同类实现可复用。一次改动，零运行时成本。

D-3命中省下的钱不进账

_serve_cached_ask 把 cost_cny / tok / elapsed 全部清零 —— 这是对的 （它描述的是“这次调用发生了什么”），但没有任何地方记“省下了多少”。 没有这个数，缓存分层做完拿不出收益证明。

修法 审计记录加 saved_cny / saved_ms（取首跑那条的值），成本页单列“缓存节省”。

D-4六份配置里的缓存单价是错的

配置写 price_cached_input_per_1k: 0.00008（标准价的 1/10）， 官方明码 0.1 元/1M，即 1/8。命中占输入的 91%，这一项几乎决定整张账单。 DeepSeek 备选单价停在 2026-09-10 降价前。

单价散落在六份配置：config/{askdb,public,sample}.yaml + evals/config/ragforge-{prod,eval,tight}.yaml，改必须六份一起； 审计是落库的既成数字，改配置只对之后的调用生效，存量不回溯。

修法 六份同步；trace.call_cost_cny 的算法本身是对的，不要动。

D-5无 singleflight，同一问题并发全部穿透

同一个问题被 N 个人同时点（站点上很常见），N 份请求全部穿透 L1，各跑一遍模型、各扣一次配额。

修法 Redis SET NX 占位 + 短等待，后到者等首跑写入。fail-open 原则不变 —— 占位超时就照常自己跑。

D-6交接出去的执行永不进缓存 —— 而那正是最贵的一批 本组最高优先级

server.py 里 cache.put(ckey, out, …) 只写在同步返回那一段。 一旦交接，函数在 if _notice is not None: return JSONResponse(_notice) 就返回了， 走的是 _settle_detached —— 它只做三件事：_stash_handoff、挂审批、烧票， 没有写 ckey。

而交接不只看 10 秒那条软阈值。async_runner.Handoff.check 在每个节点边界还判三条，任意一条成立就立刻交接： 

if   time.monotonic() >= self.deadline:        # 超 async_after_ms（生产 10s）
elif multi_step or step >= 3:                 # 多步链路
elif tok_used >= cost_cap // 2:               # token 过半（6,000）
elif explain_rows >= scan_threshold // 2:     # 预估扫描过半（250,000 行）

「商品总共有多少条记录」这类全表 COUNT 在大表上第四条几乎必中 —— 一条全表 COUNT 的 explain_rows 就是表的行数。它连 10 秒都不用等， 在第一次 _n_act 的节点边界就交接了。这句话的结果结构上不可能进缓存， 问一百遍命中零次。

后果有两条，都不是“少省一次钱”那么轻：

· 被漏掉的正是最贵的那批。能同步跑完的是便宜的短链路； 交接出去的是多步、高 token、大扫描那一批 —— 缓存本该在它们身上省得最多。
· 命中率这个数系统性偏乐观。分母里没有这批， §01 那个 73% 说的是“短链路的命中率”，不是全站的。

交接那一路的结果原本只落进 _stash_handoff 那个按 thread_id 编的临时 key， 而 thread_id 每次都是新 uuid —— 别人再问同一句话取不到。 同源的还有：as_task 与凭票重跑（approval_id）都令 _thr = 0 入口即交接， 同样永不进缓存。

修法 把 cache.put 挪进 _settle_detached，与 _stash_handoff 并列， 判据沿用同一条（ok 且 rejected_by is None；挂审批那一档已被后者挡掉）。 同步那一路的判据旁边留一句交叉引用 —— 两边不一致的后果是“同一句话，跑得快的进了缓存、跑得慢的没进”， 那是最难从现象上看出来的一种。

这六条的先后

D-6 > D-1 > D-2 > D-4 > D-3 > D-5。 D-6 决定后面三层缓存能不能对最贵的那批流量生效 —— 不先修它，L2/L3 建在同一个漏口上， 长链路照样一条都存不进去。D-1 是在漏钱，D-2 是口径正确性，D-4/D-3 是账面，D-5 是并发尖峰。

L0进程内渲染件缓存不缓存答案

qcache 模块头写得对：答案不能进程内缓存（多副本各存各的、命中不一致）。 但下面这些是确定性派生物，进程内缓存完全安全：

  • render_agent_system(cfg, hide) 的结果 —— 每轮 decide 重拼一遍，输入是 (cfg 指纹, hide 集合)
  • schema_prompt / schema_heads —— 输入是 (源指纹, tables_hit)
  • 本次请求的问题向量 —— _n_recall 已经算过，同请求内 L2/L3 直接复用，不再多调一次 embedding

收益：不省钱（这些本来就便宜），省的是每轮几十毫秒 CPU 与一次 embedding 往返。

L1精确应答缓存已有 · 四处改动
  • key 并入配置指纹（D-2）
  • singleflight（D-5）
  • 记 saved_cny（D-3）
  • 问题原文不做规范化 —— 这一条保持现状。qcache 的判断是对的： 规范化会把语义不同的两句并到同一条缓存上。规范化是 L2 的职责，不是 L1 的。
L2语义应答缓存新增 · 判定层
  • 向量从哪来：_n_recall 那次 embedding 的产物 —— 零额外成本、零额外延迟。
  • 存哪：复用同一套 pgvector 设施，另开 askdb_answer_cache（表里除向量外还存 payload 与 sql，不只是向量）。 不要混进 askdb_schema_vectors —— 那张表按 collection 指纹整体回收，会把缓存一起删掉。
  • 命中判据：cosine ≥ θ_hi（初值 0.93，靠影子跑标定）且 问题不含时间敏感词且缓存年龄 < TTL。
  • 入库门槛（比 L1 严）：ok 且 rejected_by is None 且未截断 且未降级（recall_blind / recall_degraded / mask_degraded / scope_narrowed 全假） 且 grounding 通过。
  • 索引：单源候选上千条之后再建 ivfflat，不要提前建 —— 判据照搬 vectors.py 那段说明。
L3 ★语义计划缓存 —— 本方案的核心新增 · 判定层

命中后不返回旧答案，而是取出上次的 SQL 重新执行一遍。

问题 → 向量 → 近邻(θ_lo 0.88) → 取 sql_final + answer_step + 口径模板
     → 过 guard（不跳过） → execute_sql（~15ms）→ 用新行填回答案模板 → 返回
L2 直答L3 重跑
模型调用00
数据新鲜度最多陈旧 TTL永远是当下的
成本¥0≈ ¥0（一条 SQL）
可用 TTL10 分钟可以按天算

TTL 能拉长，意味着命中率是完全不同的量级。“哪个组织的知识库最多”这类问题一周被点几十次， L2 只能收敛同一个十分钟窗口内的，L3 收敛全部。

硬约束（不可放宽）

  • 复用的 SQL 必须重新过一遍 guard 与脱敏，绝不因为“上次过了”就跳过 —— 白名单、脱敏列、租户注入都可能已经变了。
  • SQL 含字面日期（DATE '2026-07-27'）的不进 L3；只有相对时间表达 （date_trunc、NOW() - INTERVAL）或无时间的才可复用。 这一条做成确定性扫描，不靠模型判断。
  • 答案模板只做数值回填，不重新措辞。回填不上（行数 / 列名与上次不一致）即判未命中，回落模型链路。
  • 界面必须标注“结果为实时重跑、结论口径沿用某次首跑”，并给一键完整重跑。
L4厂商前缀缓存已在命中 · 还能再进一步

现在 intent 与 decide 是两套不同的 system 前缀， 同一份 schema 在厂商侧缓存了两份。§05 的“合并 intent 进 decide”会顺带把这份重复消掉。

render_agent_system 的注释已经把纪律写死了（“绝不能插入随请求变的值”）—— 这条纪律要写进评审清单：它是 91% 命中率的唯一来源，破坏它不会报错，只会账单翻倍。

明确不做的

参数化槽位替换（“华为的×” → “腾讯的×”复用同一条 SQL 换参数）：收益诱人， 但值替换要过实体识别，错一次就是答错人。等 valuelink 在生产跑稳再单独立项。

跨源共享缓存：任何情况下都不做。进程内答案缓存：见 L1 说明。

§03 那两个 θ（0.93 / 0.88）是拍的。上线当天在生产上量了一次， 被证伪的不只是取值，是"靠相似度判同不同"这个做法本身。

同义 0.755–0.889，会答错的那批 0.596–0.908 —— 最危险的一对比所有同义对都高。所以没有任何一条 θ 能把两者分开： 调高则一条都不命中（生产上看到的正是这个：stored 一直涨、命中恒 0）， 调低就会拿订单的数去答商品，而且不报错。

改法相似度只缩小候选，判据交给内容词确定性

semcache.lexically_same：去掉功能词（数量词 / 疑问词 / 量词 / 套话）之后， 两句提问剩下的内容词必须完全相同。功能词表里绝不收任何能区分问题的词 —— 数量、销售额、新增、在售、本月、商品、订单都留着，单测钉住了这一条。

同一份探针上这道判据 12/13，八条危险对全部拦下， 包括那条 0.9083 的。唯一一处错判（「各品类商品数量分布」⇄「按品类统计商品数量」被拦下） 是漏收，不是错答 —— 方向正确：漏收只多花一次钱，错答是给出一个错的 数字且不报错。

θ 顺带按实测下调到 0.82 / 0.75，但它们从此只负责 "把候选缩小到一条"。

影子档原来记漏了最要紧的一半

原实现只在命中时留痕，够不着的一概不记 —— 于是"差一点就命中"的那一片 分布一个数都拿不到，而 θ 恰恰要靠它来标定。影子档的全部意义是标定，这等于把它最该干的 事漏掉了。现在每次近邻查找都记 top-1 分数（0.05 分桶）与拒绝理由。

04语义层是判定层，必须先影子跑

L2/L3 的命中是一次判定 —— 判错的形态是“给了你另一个问题的答案”，且不报错。 按既定纪律，会改变判定结果的东西一律三档先标定。

  • 三档旋钮 semantic_cache: off | shadow | enforce，与 grounding、 coverage_check 同一套语义。
  • shadow 档做什么：正常跑模型链路，同时记录“如果启用会命中哪一条、相似度多少、 两个答案是否一致”。跑满两轮、每轮不少于 130 条、覆盖 13 个源，再定 θ。 本机样例想不出真实的误判形状，离线重放不作数。
  • 红线（任一触线不切）：接地校验 ungrounded 命中率、R-11 拦截率、OOS 拒答率、 同义问法一致性。前三条守安全，第四条是这个产品吃过亏的地方。

顺带的正收益，以及它的反面

同义问法一致性实测只有 58%（1030 次跑测的 P0 之一）。 语义簇天然把同一簇收敛到同一个答案，一致性会被拉上去。

但反面同样成立 —— 一个错答会被固化给整簇。 所以入库门槛里 grounding 那一条不能省，且界面必须能一键重跑。

05首字延迟

现状：首字时间等于整条链路时长。llm.structured() 走阻塞 invoke， /api/ask/stream 推的是 step 进度事件，不是答案内容。生产 P50 1.46s / P95 16.14s。

P0先出结果表零成本 · 零风险 · 收益最大

SQL 早就跑完，结果行躺在 last_exec 里，用户却要等收敛轮把 300–1400 个 token 写完（按 14.4ms/token 算是 4–20 秒）才第一次看到东西。

改法：ask_stream 增加事件 {"type":"partial_result", "rows":…, "sql":…, "step":n}， 在 _n_act 成功后立刻推；前端先渲染结果表 + “正在归纳结论”。

维度变化
首字时间从“全链路”降到“SQL 执行完那一刻”（P50 约 3–5s，多轮链路收益更大）
成本变化0
判定变化0（只是把已有的东西早点送出去）

注意：每一步都推，前端按 answer_step 在收尾时定版 —— 与 _answer_exec 那条已修的正确性口径一致。

P1收敛轮真流式不增加调用次数

做法：stream() 拿 tool_call_chunks 的 arguments 增量， 做部分 JSON 的容错抽取，只抽 answer 一个字段往外推； 解析失败即静默回落到整体解析（观测字段绝不能把主链路弄崩，这是项目已有的纪律）。

必须同时确认：流式下 usage_metadata 还在不在 （stream_usage=True），否则 token 与成本会整片丢 —— 那比慢更坏。

不做两段式（结构化 + 非结构化各一次）：多一次调用，与省钱目标直接冲突。

P2合并 intent 进 decide高风险 · 有前置

省：一次调用 ≈ 1.2–3s + 约 3.6k 输入 token + 一份重复的厂商缓存前缀。

风险：OOS 拒答是用户可见的判定门。合并后判据的上下文变了 —— INTENT_SYSTEM 明确要求忽略列名，而 decide 看的是全列明细， 这正是 intent_schema_heads 默认关的原因。

前置：那份 120 条生产拒答集回归必须能跑（要生产登录态）。 跑不通就不做 —— 不要为了提速把同一个前置绕过去。

P3 · 别忘了

缓存本身就是最好的 TTFT：L1/L2 命中是个位数毫秒，L3 命中约 20–50ms。 把命中率从 73% 抬到 85%+，对 P50 首字的改善超过上面任何一条。

为什么上线的是 shadow 而不是 enforce

§04 是本方案自己定的规矩：语义层的命中是一次判定，判错的形态是“给了你另一个 问题的答案”且不报错，所以必须先影子跑标定。本轮上线不改变任何一个用户 可见的答案 —— L2/L3 只记“本来会命中哪一条、命中了会不会答错”。

真正立即生效的是 L0、L1（D-6 / D-2 / D-5 / D-3）这几层：它们不是判定， 不存在判错一说。
