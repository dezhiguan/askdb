### ⚠ 对首轮 BUG-4 的更正

首轮报告称"执行报错从不触发反思"，**这个判断是错的**。实测：

| 错误 | 异常类 | 首轮实际行为 |
|---|---|---|
| 类型不匹配 | `ConversionException` | `rejected_by=None` → **本来就重试** ✓ |
| 函数用法错 | `BinderException` | `rejected_by=None` → **本来就重试** ✓ |
| 连接不可达 / 超时 | `DataSourceError` | `rejected_by=EXEC` → 不重试 |

首轮用例注入的是 `DataSourceError`，那是**基础设施异常类**，不是 SQL 错。
所以设计 §4.5 对 SQL 语义错的要求**一直是满足的**。

真正的缺陷缩小为一条：**语句超时不重试，而等价的干跑超限（R-11）会重试**
—— 两者都是"查询太重"，模型缩小范围就可能过，一个重试一个不重试属实不一致。
已修：`DataSourceError` 增加 `retryable`，超时置真、连接不可达置假。

## 二、产品缺陷（5 条）—— 均未修复

### 🔴 BUG-1（A-10，P0，安全）`tenant_filter` 缺 `{ref}` 时校验放行

**现象**：把 `documents` 的 `tenant_filter` 写成 `org_id = {ctx}`（缺 `{ref}`），
配置校验**通过**，服务正常启动。

**期望**：校验失败。`_validate` 已经检查了 `{ctx}` 缺失（A-09 通过），
但没检查 `{ref}`。

**影响**：缺 `{ref}` 时谓词无法绑定到具体的表实例。单表查询下 SQL 恰好仍然
正确，但**自连接场景（`FROM documents a JOIN documents b`）下无法区分两个别名**，
注入行为不可预期。这是一条静默的越权路径 —— 配置看着是对的，行为在特定
语法下才出错。

**定位**：`askdb/config.py` `_validate()`，只有 `"{ctx}" not in t.tenant_filter` 一处判断。

---

### 🔴 BUG-2（B-19，P1，正确性）R-03 与 R-04 对 CTE 别名的处理不一致

**现象**：
```sql
WITH documents AS (SELECT 1 AS x) SELECT x AS y FROM documents
```
R-03 正确地把 `documents` 识别为 CTE 别名、不当作真实表（所以没报表白名单错误），
但 **R-04 仍按真实表 `documents` 去校验字段**，报
`字段不存在：x（表 documents 无此列）`。

**期望**：CTE 别名遮蔽同名真实表时，两条规则应保持一致 —— 要么都视为 CTE，
要么都视为真实表。

**影响**：合法 SQL 被误杀。模型若给 CTE 起了与白名单表同名的别名，
查询必被拒且报错信息具有误导性（说字段不存在，实际是别名遮蔽）。
`_cte_names()` 的结果传给了 R-03，没传给 `_check_columns()`。

**定位**：`askdb/guard.py` `_check_columns()`。

---

### 🟡 BUG-3（C-20，P2，健壮性）重复改写会叠加租户谓词

**现象**：对已改写过的 SQL 再跑一次 `guard.check`，得到
```sql
WHERE documents.org_id = 65 AND documents.org_id = 65
```

**期望**：幂等 —— 已存在完全相同的租户谓词时不重复注入。

**影响**：**不构成安全问题**（语义等价），也**不存在于当前生产路径**
（状态机每轮都对 `sql_raw` 而非改写结果做校验）。但它说明注入逻辑不检测
已有谓词；若将来有任何一处对改写结果二次处理，SQL 会持续膨胀。
定级 P2。

---

### 🔴 BUG-4（E-09，P1，与设计文档冲突）执行报错从不触发反思重试

**现象**：让 `executor.run` 首次抛 `DataSourceError`、第二次正常，
期望 `attempts == 2`，实际 `attempts == 1` —— 直接终止，没有重试。

**期望**：设计文档 §4.5 明确写着「触发条件：静态校验未通过（R-01～R-08）
**或执行报错**。将真实错误信息与失败 SQL 一并回灌模型重新生成」。

**根因**：`_route_after_execute` 对 `rejected_by == "EXEC"` 一律返回 `finalize`，
注释写的是「数据源不可用不是模型的错，重试没有意义」。

**问题在于 `EXEC` 把两类错误混为一谈**：

| 错误 | 重试有意义吗 |
|---|---|
| 连接断了、库不可达、超时 | ❌ 注释说得对 |
| 类型不匹配、除零、函数用法错、字符集问题 | ✅ **模型据错误能改对，设计也是这么要求的** |

后者现在一次都不会重试。这与 §4.5 直接冲突 —— 要么改实现（按错误类别细分），
要么改文档（承认执行报错不重试）。**需要产品决策，不是单纯的代码 bug。**

---

### 🟡 BUG-5（F-05，P1，与文档冲突）`min_score` 未被严格执行

**现象**：设 `min_score = 0.95`，注入相似度 0.99 与 0.10 的两张表，
**0.10 那张仍被注入**。

**期望**：`config/askdb.yaml` 对该项的注释写的是
「相似度低于此值的表/口径视为干扰，**不注入**」，设计文档 §3.2.3 同义。

**根因**：`schema_rag.recall()` 的向量分支里有一段保底逻辑 ——
```python
picked = [t for s, t in ranked if s >= min_score][:max_k]
if len(picked) < top_k:
    picked = [t for _, t in ranked[:top_k]]   # ← 阈值在这里被绕过
```
注释说「宁可多给一张，也不要让模型无表可用」。这个取舍本身可能是对的，
但**它让 `min_score` 在过线表少于 `top_k` 时完全失效**，与配置注释和设计
文档的表述不符。

**建议**：保留保底逻辑，但改注释与文档措辞（例如"低于阈值的表在有足够
高分表时不注入"），或把保底数改为可配置并默认 1。**需要产品决策。**
