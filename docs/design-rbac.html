1背景与目标

askdb 已上线 5 个内置角色、10 名内置人员、8 个功能页。但角色目前只对「查数」这一条路径生效，且只有两个维度（可见表、行上限）； 权限页上展示的其余维度与策略多数没有后端执行。

本设计的目标：把「页面上宣称的权限」与「运行时真正执行的权限」对齐，并在不新增角色、不调整人员归属的前提下， 为现有每一项功能明确责任边界。

1.1三条设计原则

  1. 每一条权限都要对应一个具体的执行动作。落不到护栏或接口拦截上的条目，宁可在页面上标注「未接入」， 也不放进矩阵充数 —— 这是 identity.py 里「角色固定不开放自定义」那段注释已经确立的原则，本设计沿用。
  2. 只能收窄，不能放宽。沿用 identity.policy_for / narrow 的既有语义： 配置与内置默认取交集，角色叠加取并集，但每个策略本身都是实例白名单的子集。
  3. 职责分离 —— 并且提出与放行分属两人。管人的不看数据（已内置），改数据边界的不自己用这个边界查数。
V1.1 决定 · 全部审批闸门收敛到系统管理员 它带来一条结构性保证：系统管理员的内置策略是 Policy(tables=frozenset(), max_rows=0)， 永远不可能是查询的发起人，因此自批在结构上不可能发生 —— 这不靠流程约定，靠的是已经写死在 DEFAULT_POLICIES 里的零表默认。
代价 审批人必须看到问题原文与最终 SQL 才能判断该不该放行，所以「系统管理员不看查询内容」这条要在审批场景内放宽（见脚注 12）。 放宽的是可见性，不是数据权限 —— 审批通过后任务以发起人的角色恢复执行，审批人拿不到任何结果集。

2.3必须先处理的六个缺陷

D-1 · 高 · 环境范围形同虚设 _cfg_for(source) 只按 id 取源，取完才按角色收窄表与行数。角色对「能连哪个库」没有任何约束 —— 只要数据源列表里有生产只读镜像，测试角色照样能选中并查询。sources.py 里 Source.env 字段的注释写得很直白 —— 「环境标签，仅用于界面区分，不参与鉴权」。角色详情第一格 STAGING 因此是 页面上唯一一个看起来是真值、实际不成立的字段，比纯占位更有误导性。

附带一个规模问题：env 的取值只有 test 与 prod_ro 两种 （build() 里非法值一律回退 test），而角色 scope 区分了 DEV + STAGING 与 STAGING 两档。 枚举撑不起角色已经宣称的粒度，需一并扩展。
D-2 · 高 · 数据源写接口只有部署级开关，没有请求方身份判定，且是提权路径 POST /api/sources、PUT /api/sources/{id}/tables、DELETE /api/sources/{id} 走 _sources_gate()，它校验的是实例开关 datasources.allow_runtime_add 与频率限制 —— 是「这个实例允不允许」，不是「这个人允不允许」；函数签名里连 request: Request 都没有，拿不到调用方身份。 config/askdb.yaml 当前该开关为 true，即任何能打开页面的人都能调。 其中改白名单直接决定 cfg.tables —— 一次无身份判定的白名单写入，等于给所有角色同时放宽可见表， 绕开了「只能收窄」这条不变量的全部保护。
D-5 · 高 · MCP 通道完全绕开角色 askdb/mcp_server.py 的 build_server(cfg) 直接持有启动配置， ask / run_sql / schema 三个工具都不经过 _scoped()， 以实例白名单全量运行，没有角色、没有身份、没有 user 字段。护栏与只读约束仍然生效（这条通道不能写数据）， 但「谁能看哪些表」这一层在这里是空的。对外接入的 Agent 因此拥有超过任何内置角色的可见范围，且审计里的 user 为空。
D-3 · 高 · 未登录拦截只覆盖了查询路径，治理面没拦（实测确认） 2026-09-05 对本机实例（127.0.0.1:8011，auth.required: true）不带任何会话 cookie 逐个打接口：
接口无会话时

/api/audit/stats200

匿名从 /api/audit 拿到的单条记录含 user、role、question 三个字段 —— 即「谁、以什么角色、问了什么原话」，1502 条全都可翻。

根因是 _require_login 靠逐接口手工调用来覆盖，全仓只挂在 /api/ask 与 /api/sql 两处（/api/tasks 自己写了一份等价判断）；没有中间件、没有全局 Depends。 审计中心保护的是「谁查了什么」，它自己不设门。
D-4 · 中 · 复放是一条按原记录权限读取的通道 /api/replay 默认关闭（observability.replay_api）、有字段白名单与限流，这几层做得很扎实； 缺的是调用方是谁这一层。开关一旦打开，低权限者拿到 trace_id 即可读到数据负责人查询的最终 SQL 与执行链路。
D-6 · 中 · 导出不经服务端，导出权限无处施加 审计中心的「导出审计报告(CSV)」与执行追踪的「导出 OpenTelemetry」都是浏览器端把已拉取的数据拼字符串下载， 没有后端导出接口。这意味着权限页宣称的 AGG ONLY「导出权限」维度在当前架构下没有任何可施加的位置 —— 数据一旦进了页面就已经出去了。真正的控制点在 A-01/A-03 的读取范围，不在导出动作本身。

4.1脚注

  1. 直查绕过模型与业务口径层。产品角色的价值恰恰在口径归口，给它一条绕开口径的通道会让「指标以谁为准」失去落点。 这是职责收敛，不是安全考虑 —— 直查同样过全部护栏。
  2. 业务表可见，成本与用量类表（token、计费、模型调用明细）不可见 —— 沿用 config/public.yaml 已确立的口径：「产品角色看业务不看账」。
  3. 仅测试库与模拟数据表，不含任何承载生产语义的表。
  4. 开发角色只作用于非生产环境，环境本身已无真实个人信息；对从生产只读镜像同步来的样本表仍强制脱敏。
  5. 数据负责人对高成本查询与敏感字段同样需要申请，由系统管理员放行（V1.1）。全域可见不等于无需审批 —— 前者是范围，后者是闸门。
  6. 开发角色可见他人任务的元数据（发起人、状态、耗时、失败原因），不可见问题原文与结果集 —— 排障需要的是前者。
  7. 仅列出本角色环境范围内的数据源。列表本身就是信息：不该让测试角色知道生产只读镜像的存在与连接目标。
  8. 系统管理员可见运维健康面（连通性、自检、质量指标），不可见任何业务数据与查询内容。 这是对内置 Policy(tables=frozenset(), max_rows=0) 的补充说明，不是放宽。
  9. 开发角色仅对 env ∈ {dev, test} 的数据源可增删改；生产只读镜像的任何变更一律走审批链。
  10. 产品角色是口径的业务归口，但口径落地为配置文件，变更走评审。产品提出、数据负责人确认、代码评审合入 —— 页面不提供编辑入口是有意的。
  11. 开发角色中承担口径与黄金集维护职责者（赵珂）可提交口径变更，仍需数据负责人确认。
  12. 分两种场景，可见范围不同（V1.1 修订）：
    • 日常审计浏览：仅见操作元数据（谁、何时、走哪个源、被哪条规则拦下、扫了多少行），不见 question 与 sql_final。
    • 审批待办：对进入待审批队列的那一条，可见 question、sql_final、explain_rows、涉及表 —— 不看这些无法判断该不该放行，一个盲批的审批人比没有审批更糟。
    两种场景下都不可见结果集（rows 本就从不写入审计文件，见第七节）。审批动作本身留痕，事后可核「管理员看过哪些查询内容」。
  13. 复放必须按复放者本人的角色重新收窄，不得沿用原记录的角色（见 D-4）。
  14. 系统管理员对策略只读，不可写。管人的角色若能改数据策略，等于绕一圈拿到数据权限 —— 这与内置的零表默认是同一条原则。
  15. 现有 env 枚举只有 test / prod_ro 两值，撑不起开发与测试的区分。需扩为 dev / test / prod_ro 三值，开发角色取前两者、测试角色仅取 test； 在枚举扩展落地前，开发与测试在环境维度上等价。
  16. 数据负责人负责判断变更在业务上是否成立（这张表该不该开、这个源该不该接），系统管理员负责放行。 提出与放行分属两人，任何一次数据可见范围的扩张都需要两个人同意 —— 这是 V1.1 把审批收敛到系统管理员后最直接的收益。

5.1两个必须先确认的问题

阻塞项 · 人员核对 权限页显示系统管理员 2 人，而 config/askdb.yaml 的 auth.accounts 里只有徐婷一人。 差额来自身份库 askdb_role_members 中一条手工登记、auth_user_id 为空（未绑定网关用户）的记录。 V1.1 之后，这意味着一个身份未经核实的账号持有全部审批权。上线前必须查明并处置。
单点风险 · V1.1 后位置变了 审批不再压在何静身上，而是全部压在系统管理员上。核实完成后若确认系统管理员实为徐婷一人，需要一名备份审批人。 可用 RBAC 的加法语义（identity.combine 已支持多角色叠加）给某位成员叠加 SYS_ADMIN —— 不新增角色、不调整人员，只在成员表里多一条登记。 备份人选不能是何静：她是数据源变更的提出方，兼任放行方会让「提出与放行分属两人」失效。

6落地路径

阶段一 鉴权兜底 · 2026-09-08 ~ 2026-09-19

目标：把裸奔的接口关上。这一阶段不引入任何新权限维度，只让「已有的角色」覆盖到「已有的接口」。

  1. 登录判据从逐接口调用改为默认要求，白名单显式列出：/api/health、/api/auth/*、 /api/identity/roles、静态资源。当前 _require_login 只挂在 4 个接口上， 靠「记得加」来保证覆盖，接口一多必漏。
  2. /api/sources 的三个写接口（S-03/04/05）接入审批链；/api/introspect、 /api/identity/members、/api/audit、/api/replay 按矩阵设门。
  3. 审计与追踪按 user 字段做可见范围过滤 —— 审计记录里已经有 user 与 role 两个字段，不需要新增存储。
  4. 复放改为按复放者当前角色调用 _scoped() 重新收窄（D-4）。
  5. MCP 通道纳入角色体系（D-5）：build_server 接收一个角色码（由启动参数或调用方凭据指定）， 内部改走 identity.for_role(cfg, role)，默认值取最保守的角色而非全量配置；审计记录补上调用方标识。 在此之前，MCP 服务不应对内网以外开放。
验收 以每个角色的账号登录，逐条走矩阵，越权项返回 403 且文案指向「当前角色无此权限」而非通用护栏措辞。

阶段二 让环境范围成立 · 2026-09-22 ~ 2026-10-10

目标：消除 D-1，使 role.scope 从展示字符串变为执行判定。

  1. Source.env 字段已存在，需要做的是两件事：把枚举从 test / prod_ro 扩为 dev / test / prod_ro（已有数据源回填），并删掉「不参与鉴权」这条注释所描述的现状 —— 让它真正参与判定。
  2. Policy 增加 envs 维度，语义与 tables 一致：收窄、取交集、多角色取并集。
  3. _cfg_for(source) 之后增加环境归属校验；/api/sources 列表按环境过滤（脚注 7）。
  4. 权限页四格中的「环境范围」改为读取真实生效值。
验收 测试角色账号在数据源列表中看不到生产只读镜像；直接构造请求指定其 id 返回 403。

阶段三 脱敏与数据期限 · 2026-10-13 ~ 2026-10-31

目标：P03 与「数据期限」落地。两者都可复用现成机制，不需要新造判定。

  1. 列级脱敏：Policy 增 masked_columns（按列名模式匹配）。落点在执行器返回前的结果处理； R-05 展开 SELECT * 时已经拿到了真实列名，脱敏所需的列信息现成。
  2. 数据期限：Policy 增 max_age_days，复用 R-10 的强制谓词注入机制 —— R-10 已经在做「给 SQL 强制注入租户谓词」，时间窗口是同一类动作，注入一个时间条件即可，不需要新的护栏规则。
  3. 权限页去掉 ROLE_LIMITS 硬编码，改读后端真值。
验收 产品角色查询个人信息列返回脱敏值；查询 90 天前的数据返回空集且执行计划中可见注入的时间谓词。

阶段四 审批闭环 · 2026-11-03 ~ 2026-11-21

目标：P07 落地，三条审批链共用同一个队列。

  1. R-11 已在执行前用 EXPLAIN 估算扫描行数，阈值判定的输入现成。
  2. 超阈值不再直接拒绝，而是把任务置为「待审批」落入任务中心 —— 任务中心已有断点续跑的执行线程模型，挂起与恢复是同一套机制。
  3. 系统管理员在待审批队列审批（V1.1）。通过则以发起人的角色恢复执行 —— 不是审批人的角色，也不可能是：审批人内置零表，用它的角色恢复只会立刻撞上 _require_scope。
  4. 审批动作独立留痕，记录审批人、时间、决定，以及审批人查看了哪条查询的原文。
  5. 同一批次落地另外两条审批链：敏感字段按需放开（Q-06）、数据源与白名单变更（S-03/04/05）。三条链共用同一个待审批队列与同一套留痕。
验收 测试角色发起一条预估扫描超阈值的查询，任务进入待审批；徐婷账号批准后任务恢复并完成，审计中同时存在发起与审批两条记录。 补充两条反向用例：何静账号对该条审批返回 403（数据负责人无放行权）；何静自己发起的超阈值查询同样进入待审批，且她本人批不了。

不做的部分

P11 结果禁止用于模型训练

在没有导出功能、结果不落盘的当前架构下，这条已经由「结果只在任务生命周期内处理」天然成立。 不新增开关，改为在权限页把它标注为架构约束而非可配置策略 —— 一个永远为真且拨不动的开关，比没有这个开关更容易让人误判。

导出权限 / AGG ONLY

没有导出功能（D-6），这一维度暂不定义。若后续引入导出，需同步定义「聚合结果」的判定标准 —— 是否含 GROUP BY 不足以判定，SELECT id FROM t GROUP BY id 仍是明细。

策略开关的持久化（I-04）

阶段一至四中，P01/P03/P07 的开关状态由配置文件承载，权限页保持只读展示。 把策略做成页面可拨的开关，意味着策略变更没有评审、没有版本、没有回滚 —— 那是比「开关拨不动」更严重的问题。

附 · RBAC 与租户隔离是两套正交机制

本设计只讨论 RBAC。需要明确的是，它与已有的租户隔离解决的不是同一个问题，不能互相替代：

控制什么实现配置
角色（RBAC）能看哪些表、哪些列 Policy.tables → cfg.tables → R-03role_policies
租户（Tenant）同一张表里能看哪些行 R-10 强制注入 org_id 谓词 + PostgreSQL RLS 双保险 tenant 段，on_unresolved: reject

两者叠加才是完整边界：角色放行了 documents 表，租户仍然只让你看到自己组织的行。 本设计新增的三个维度中，数据时间窗口（Q-07）与租户属于同一类（都是行级收窄、都靠谓词注入）， 因此阶段三复用 R-10 的机制是顺理成章的；而脱敏（Q-06）是列级，属于角色这一侧。
