00 / DECISION

设计结论

保留现有单 Agent 快路径，在复杂请求上增加顶层 Supervisor。多智能体不是默认路径，而是按复杂度、数据域和验证需求动态启用。

把 askdb 改造成“快路径 + 多智能体任务图”，而不是让所有问题都进入多 Agent 会议。

不可改变的三条边界

  • 权限、租户、脱敏由 Runtime 决定
  • 每条 SQL 继续独立经过现有安全原子
  • 最终结论必须引用结构化 Evidence
CURRENT / 单智能体

一个循环承担全部职责

当前 recall → intent/fast → decide → act → ground → finalize 已能稳定完成单源查数，但计划、取证、复核和表达由同一决策主体完成。

TARGET / 协作式

职责分离，证据汇合

Supervisor 管任务图，Semantic 管口径，Worker 管取证，Verifier 管质量，Synthesizer 管表达；只有 Evidence Store 是共享事实源。

01 / WHY

为什么要拆成多智能体

不是因为当前功能不可用，而是单循环在任务复杂度提高后会出现职责冲突、上下文膨胀、难以并发和自我复核失真。

LIMIT 01

规划与执行相互污染

同一个模型既决定查什么，又根据自己的查询结果判断是否正确，容易围绕第一条错误假设持续修补。

LIMIT 02

复杂问题无法真正并行

多个相互独立的指标目前仍在一个 decide/act 循环里串行推进，延迟随子问题数量线性增长。

LIMIT 03

跨源上下文不成立

当前一次请求绑定一个 source，状态里只有一个 cfg、executor 与 last_exec，无法自然表达多数据源取证。

LIMIT 04

自我复核不够独立

生成 SQL、解释结果和数字接地都围绕同一段历史。验证更像“检查自己的作业”，缺少独立目标与失败分类。

LIMIT 05

失败只能整链重试

没有稳定的子任务与证据 ID，某一项失败后很难只重跑该项，恢复、去重和局部降级都不够精确。

LIMIT 06

最终答案与证据耦合偏弱

现有 exec_results 能做数字接地，但尚未形成“每条 Claim 明确引用哪些 Evidence”的强契约。

拆分触发条件：多实体、多指标、跨数据源、需要独立核对、存在可并行子问题或需要结果驱动分支。单表计数、普通分组、Top-N 和单条 SQL 可表达的问题继续走现有快路径。

03 / ROSTER

拆成五类智能体

五类是职责类型，不代表每次固定启动五个进程。简单问题启动零个新增 Agent；复杂问题通常是 1 Supervisor + 1 Semantic + 1～3 Worker + 1 Verifier + 1 Synthesizer。

5 类

运行时动态生成 3～8 个实例。Query Worker 是可水平扩展的同构角色，不按业务域复制大量永久 Agent。

Recommended boundary
A1

主管智能体

SUPERVISOR

拥有全局目标，但不直接查库；维护任务图并决定下一步调度。

  • 拆解与依赖排序
  • 预算与并行度分配
  • 失败降级和局部重试
  • 判断是否需要人工介入
禁止：execute_sql、修改权限、绕过验证
A2

语义智能体

SEMANTIC

把用户意图固化为可执行契约，减少各 Worker 对同一口径的重复猜测。

  • 指标与维度解析
  • 统计粒度与时间窗口
  • 候选数据源与关联键
  • 生成 QuerySpec
禁止：直接给最终数字、访问不可见源
A3

查询智能体

QUERY WORKER

每个实例绑定一个 source scope，只完成一个原子子任务并产出 Evidence。

  • Schema 召回与 SQL 生成
  • 调用现有安全 SQL 原子
  • 结果形状与截断检查
  • Evidence 标准化
禁止：自由选择其他数据源、生成总答案
A4

验证智能体

VERIFIER

从独立目标检查证据是否足以支持问题，而不是润色已有答案。

  • 总计与分项一致性
  • 时间、去重、软删除口径
  • 跨源冲突检测
  • 发出受限 VerificationTask
禁止：推翻代码护栏、直接修改 Evidence
A5

合成智能体

SYNTHESIZER

只读取已验证证据，生成面向用户的结论、限制说明和证据引用。

  • Claim → evidence_ids
  • 结论与口径说明
  • 冲突和缺失如实披露
  • 选择主结果表
禁止：调用数据库、补写不存在的数字
04 / SKILL LAYER

这一期同时建设 Skill 能力层

askdb 当前已有 skill.py，但主要是“通用规则 + YAML 追加规则”后整体拼入系统提示。多智能体需要把它升级成可注册、可选择、可版本化、可授权、可评测的能力包。

Skill 不是 Agent，也不是 Tool

Agent 是承担任务的决策角色，Tool 是可执行的原子能力，Skill 是教某类 Agent “在特定业务场景里应该如何判断和行动”的可复用方法包。Skill 不独立运行，而是在创建 Agent 实例时由 Runtime 解析并绑定。

Agent 角色＋最小 Tool 权限＋Resolved Skills＝本次 Worker

安全不变量

Skill 只能提供方法、语义约束、示例和校验规则，不能授予权限、扩大数据源范围、绕过 Guard、改变审批结论或直接执行任意代码。Skill 请求的 Tool 必须与 Runtime 允许集求交集。

能力只减不增：effective_tools = runtime_allowed ∩ agent_profile ∩ skill_requested
TYPE 01

通用数据方法 Skill

实体接地、软删除、枚举查证、缓存计数器不当真值、结果截断处理。由所有数据 Agent 默认继承。

TYPE 02

领域语义 Skill

订单、支付、知识库等领域的指标定义、实体关系、默认时间和常见误区，主要绑定 Semantic 与 Verifier。

TYPE 03

数据源 Skill

某个 source 独有的表选择、方言、枚举、软删除和已知质量问题，只能绑定该 source 的 Query Worker。

TYPE 04

分析模式 Skill

同比、环比、漏斗、留存、Top-N、异常归因等查询模板和验证清单，由任务意图触发。

TYPE 05

验证 Skill

定义结果形状、总分一致、分母、去重、基准期与容差，主要供 Verifier 生成确定性的检查项。

TYPE 06

表达 Skill

面向运营、管理层或开发者的回答结构，只影响呈现，不改变 Evidence、数字和权限。

01 / DISCOVER候选发现按 agent_role、intent、source、tables、metrics 和领域标签找候选 Skill。
02 / FILTER权限过滤剔除未发布、已撤销、越出 source scope 或角色不允许的 Skill。
03 / RESOLVE依赖与冲突展开 requires；deny 优先；同级冲突失败关闭或请求人工选择。
04 / PIN版本固定任务开始后记录 skill_id、version、checksum；恢复时可追溯同一版本。
05 / BIND按 Agent 注入方法注入 Prompt，约束注入 QuerySpec/Verifier，Tool 请求仍过 Runtime。
Manifestid、version、owner、status、agent_roles、source_scopes、triggers、priority。
Instructions给 Agent 的方法论，不允许携带密钥、数据库连接或越权指令。
Constraints可机器执行的指标、维度、结果形状和验证规则，优先于自然语言提醒。
Examples少量正反例；按需检索，不把整个 Skill 库全部塞进上下文。
Tests触发、拒绝、SQL 形状、口径和回归用例；发布前必须通过。

05 / PROTOCOL

智能体如何相互协作

不让 Agent 自由聊天。所有协作通过共享黑板上的结构化产物完成；每种产物都有版本、作者、输入引用、Skill 绑定和幂等指纹。

TaskPlanSupervisor 输出。定义目标、子任务、依赖、分配的数据源和预算。
QuerySpecSemantic 输出。定义指标、维度、过滤、粒度、时间、期望结果形状。
EvidenceWorker 输出。封装 SQL、结果、数据时间、脱敏、护栏、截断与来源。
ReviewVerifier 输出。PASS / REPAIR / CONFLICT / INSUFFICIENT，并指向具体证据。
ClaimSynthesizer 输出。每条结论绑定 evidence_ids 和派生公式。

06 / ORCHESTRATION

四种编排路径

用户无须手动选择 Agent 或 Skill。Router 决定路径，Skill Resolver 决定每个 Agent 实例本次装载哪些能力包，并允许在调试模式查看选择理由。

路径 A · 保留现有快路径

例如“本月支付订单有多少”。不启动新增 Agent，继续使用现有 recall/fast/execute/finalize，避免多 Agent 固定税。

01Gateway权限、源与缓存
02Recall召回完整 Schema
03Fast SQL一次结构化生成
04Safe Execute现有安全原子
05Ground数字接地
06Return同步返回

路径 B · 复杂单源并行

例如“分析订单下降原因，分别看渠道、地区、商品类别”。Supervisor 拆成三个无依赖子任务，Worker 并行取证，Verifier 检查各口径一致后合成。

01Supervisor拆成三个维度
02Semantic统一基准期与指标
03Workers × 3并行查询
04Evidence三个证据对象
05Verifier总分与时间一致
06Synthesis原因排序与限制

路径 C · 跨数据源联邦取证

例如“活动访问后的支付转化率”。订单库和行为库分别聚合，Runtime 只允许通过已登记关联键或统一维度组合 Evidence；默认不搬运两边原始明细。

01Source Plan选行为源与订单源
02Approval命中跨源策略时挂起
03Workers × 2各源内先聚合
04Combine按批准键组合证据
05Verifier时间窗、分母对齐
06Synthesis带双源引用返回

路径 D · 只返工失败子任务

Verifier 不修改 Worker 的结果，而是提交 RepairTask。Supervisor 按问题类型重跑对应 Worker；最多两轮，仍失败则带限制收敛或转人工。

01Review发现分项缺总计
02RepairTask指向 st_channel
03Worker Retry新 evidence_id
04Supersede旧证据不删除
05Re-verify最多两轮
06Converge成功或如实降级
07 / STATE

状态机、并发和恢复

多智能体的难点不是调用多个模型，而是并发状态合并、幂等、恢复和预算。每个子任务必须有稳定 ID，并固定本次使用的 Skill 版本，不能依赖“history 最后一条”。

CREATED→PLANNING→DISPATCHING→RUNNING→VERIFYING→SYNTHESIZING→COMPLETED
RUNNING→WAITING_APPROVAL→RESUMING→RUNNING／WAITING_CLARIFICATION／FAILED／CANCELED
PARALLEL REDUCER

按 ID 合并，不覆盖列表

subtasks_by_id、evidence_by_id 和 reviews_by_id 使用显式 reducer。并行 Worker 返回时只写自己的 key，防止最后写入者覆盖其他结果。

IDEMPOTENCY

一次子任务只产生一个有效版本

幂等键由 task、subtask、source、QuerySpec、scope fingerprint 和 schema version 组成。重试生成新 Evidence，并用 supersedes 关联旧版本。

恢复前重新校验：用户权限、数据源状态、Schema 版本、语义版本和审批票必须重新检查。Checkpoint 是执行现场，不是永久授权。
08 / UX

前端需要改，但不应变复杂

普通用户仍然只看到提问框和答案。多智能体和 Skill 细节以可折叠的“执行计划”“已装载能力”和“证据”呈现；高级用户可以观察、干预和复核。

09 / FAILURE MODES

多智能体与 Skill 会带来的问题

Agent 数量增加会放大成本、状态、权限和错误传播；Skill 若缺少生命周期，也会把错误方法论稳定复制给所有 Agent。下面这些必须提前治理。

风险严重度典型表现治理策略
调用放大HIGH一个问题拆成十几个模型与 SQL 调用，成本和延迟失控。max_workers、max_parallel、全局/子任务 token 与 SQL 预算；简单题永不进入多 Agent。
错误级联HIGHSemantic 的错误口径被所有 Worker 同时执行，错误看起来更一致。QuerySpec 版本化；高风险指标先做确定性语义校验；Verifier 检查原问题与 QuerySpec。
上下文污染HIGH数据库文本或某 Agent 输出被下一 Agent 当成指令。结构化 Schema、字段白名单、数据/指令分区、转义和最大长度；禁止自由 Agent 对话。
并发覆盖HIGH多个 Worker 同时写 state，部分 evidence 丢失或 last_exec 指错。map/reducer 状态；按稳定 ID 写入；不可依赖 append 顺序与最后一条结果。
权限扩散HIGHSupervisor 或 Worker 因跨源任务获得超出用户的可见范围。Runtime 计算 scope；每个 Worker 注入最小 cfg；source_id 不由 LLM 自由提供。
验证死循环MEDVerifier 不断要求重查，Worker 不断产生近似结果。repair_rounds≤2；重复指纹检测；失败分类；到限后如实收敛或转人工。
跨源假 JoinHIGH名称相同但语义不同的字段被当成关联键，结果合理但错误。只允许登记的 JoinContract；记录基数、时区、粒度；默认先聚合后组合。
恢复时越权HIGH任务创建后权限被收回，续跑仍沿用旧 Checkpoint。Resume 前重算 scope fingerprint；不一致则重新计划或拒绝恢复。
缓存混用MED不同计划、源组合或语义版本复用了旧答案。缓存键加入 plan、sources、scope、semantic 与 schema fingerprint；跨源缓存默认关闭。
不可解释的共识MED多个 Agent 投票得出答案，但没人能指出原始数据。不采用“多数票即真”；每条 Claim 必须绑定通过验证的 Evidence。
Skill 冲突HIGH两个 Skill 对同一指标、时间或软删除给出不同规则，加载顺序悄悄决定结果。Manifest 显式声明 conflicts；硬约束冲突 fail-closed；Resolution Report 记录选择理由。
Skill 供应链HIGH未经评测的 Skill 被发布，或 Skill 夹带越权工具、提示注入和敏感配置。草稿/影子/发布流程、owner 审核、checksum、静态扫描、工具求交集、禁止秘密与任意代码。

11 / DELIVERY

四阶段落地路线

Skill Registry 与多智能体基础设施在同一期交付：先建立证据和 Skill 协议，再引入 Agent 协作；先单源，再跨源。

  • Evidence/Claim 协议
  • SkillManifest/Registry

  • Resolver 与版本固定
  • Trace 记录 Skill 绑定

12 / ACCEPTANCE

怎么判断改造成功

不能用“启动了几个 Agent”或“安装了几个 Skill”衡量成果。成功标准是复杂问题更正确、技能选择可解释、局部失败可恢复，同时简单问题不变慢。

0未授权源 / 表 / 字段访问
100%数值 Claim 绑定 Evidence
≤ 2单子任务最大返工轮数
≈ 0%简单问题新增延迟
  • 复杂任务黄金集准确率显著高于现有单 Agent 基线
  • 相同问题的 token 和 SQL 调用有明确上限
  • 并行 Worker 不发生 state 覆盖或证据丢失
  • 任一 Worker 崩溃后可从最近 Checkpoint 局部恢复
  • 权限变更后旧任务不能沿用旧 scope 续跑
  • Verifier 失败能定位到具体 subtask/evidence
  • 跨源组合只使用批准的 JoinContract
  • 前端可从结论定位 SQL、数据源和数据时间
  • 取消任务后停止未开始的 Worker 并回收预算
  • 缓存不会跨 source/scope/semantic version 复用
  • 每个 Agent Span 记录实际 Skill id、版本、checksum 与选择理由
  • Skill 无法扩大 Runtime 授予的 Tool、数据源、表和字段权限
  • Skill 冲突、循环依赖、缺失依赖和未发布版本均在执行前被拒绝
  • Skill 可按版本 shadow、发布、停用和回滚，任务恢复可追溯原版本
  • Agent 原始思维链不进入普通用户界面
  • 现有 Guard、审批、审计和脱敏测试全部保持通过
Final recommendation

先建立共同事实，
再让智能体协作。

多智能体编排真正的承重墙不是 Prompt，而是结构化任务、最小权限、Evidence Ledger、并发状态合并、预算和恢复。askdb 已经拥有可靠的 SQL 安全原子；下一步应该围绕这些原子建立协作控制面。

FIRST IMPLEMENTATION SLICE
  1. 增加 Evidence 与 SkillManifest 协议
  2. 实现 Skill Registry/Resolver，兼容现有 rules
  3. 让现有单 Agent 输出 Evidence/Claim 并记录 SkillBinding
  4. 新增 SupervisorGraph：两个 Worker + 一个 Verifier
  5. Agent 与 Skill 一起 shadow 跑黄金集和真实流量
