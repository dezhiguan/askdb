一条可用来估算的延迟公式

对最近 32 条链路按 stage 聚合（intent / select / assess / converge / reflect 五类，共 104 次调用）做最小二乘，得到一条拟合很紧的直线。它决定了后面每条改动值不值得做。

调用耗时 ms ≈ 1,170 + 14.4 × 输出 token
即：每次模型调用有约 1.2 秒的固定开销，解码速率约 69 token/秒。 推论有三条 ——
  • 砍掉一次往返 = 省 1.2 秒 + 那次的解码时间。轮数是第一杠杆。
  • 少写 100 个输出 token = 省 1.44 秒。输出长度是第二杠杆。
  • 输入 token 几乎不进这条式子（本条 66.6% 命中缓存，命中价是全价的 1/10）。"提示词太长"不是这条链路的问题。

四个缺陷

按"确定性 > 概率性"、"改代码 > 改措辞"排序。前三条互不依赖、都是确定性改动，可以并行落；第四条要按既定纪律先影子跑两轮再切。

C1

写好的答案被丢掉，用户拿到的是兜底句

代码 · 确定性

第 08 步花了 14,793 ms / 693 个输出 token，其中 815 字是一份完整答案 —— 口径说明、结论、要点三段齐全，还主动点出了库里存在多个同名「个人组织」、必须靠 org_id 区分：

知识库最多的组织是 org_id=313「个人组织」，共 35 个知识库，明显领先第二名（66「米果科技有限公司」13 个）……注意库里存在多个同名"个人组织"，靠 org_id 区分，不能只看名称。

模型把它填进了 AgentAction.answer，但同时还填了 tool=execute_sql、finish=false。而 agentgraph._n_decide 只在 finish 为真时回写 state：

if finish:
    out["answer"] = action.answer or ""
    out["answer_step"] = int(getattr(action, "answer_step", 0) or 0)

于是这 815 字从未进入 state。链路随后跑满 6 步，_n_finalize 落到 if not answer 分支，用户看到的是：

（未在预算内完成归因）达步数上限 6，收敛作答。以下为最后一次查询执行的原始结果，请直接看结果表。

外加第 09 步那张 11 行的裸表。审计里这条记 ok=true、rejected_by=null —— 从任何一个面板上都看不出用户其实没拿到答案。

"答案被丢弃"这个形态在抽样的 35 条多步链路里目前只见到这一条，但它的上游 —— 跑满上限、没有 converge 收尾 —— 出现了 10 条（29%），全部落到同一句兜底。这 10 条在最后一次成功查询之后还合计烧掉 45,655 ms / 69,618 token。

  • (a) 草稿答案也要收下。_n_decide 在 finish=false 但 action.answer 非空时，把它写进 state 的一个 draft_answer 字段；_n_finalize 的兜底分支优先用它，而不是那句"请直接看结果表"。今天这段文字是被丢掉的，用它只会严格更好；接地校验照常读 answer，不放宽任何判定。
  • (b) 最后一轮不摆工具。_hidden_tools 增加一条：_step_cap(state) - step <= 1 时把全部工具撤出规格表，并把 AGENT_USER 的 steps_left 那行改成"这是最后一轮，只能作答"。跑满上限从"没有归因"变成"有一轮明确的收尾"。

C2

三段以上的 UNION 一律拒答 —— 脱敏判定的解析 bug

代码 · 确定性

第 07 步这条枚举探查被 P03 从严拒绝，代价是 119 ms 加上第 08 步里重新规划的那一段：

SELECT 'kb_status' AS dim, status AS val, COUNT(*) AS n FROM knowledge_bases GROUP BY status
UNION ALL SELECT 'doc_file_type', file_type, COUNT(*) FROM documents GROUP BY file_type
UNION ALL SELECT 'doc_chunk_type', chunk_type, COUNT(*) FROM documents GROUP BY chunk_type
ORDER BY 1, 3 DESC

SQL 本身完全合法。根因在 guard.sensitive_output_columns —— 它只拆二元 Union：

if isinstance(root, exp.Union):
    sides = [root.this, root.expression]
    for s in sides:
        if not isinstance(s, exp.Select):
            return None          # ← 三分支时 root.this 是 Union，从这里出去

而 sqlglot 把 A ∪ B ∪ C 解析成 Union(Union(A, B), C)。本机 sqlglot 30.18 复现（pin 是 >=25.0）：

3-branch | root= Union | this= Union   | expression= Select
2-branch | root= Union | this= Select  | expression= Select

返回 None → Executor._mask 抛 MaskUnresolved → 整条查询拒答。也就是说，任何数据源上任何三段及以上的 UNION 查询都必然被拒，与是否真的涉及个人信息无关。而"先用一条 UNION 把几个枚举列的分布一次查清"正是多步链路最常用的探查写法。

修法是把 Union / Except / Intersect 递归展平到叶子 Select，再按位置对齐取并集。方向是变严不是变松：从"整条拒答"变成"该打码的照常打码"。

改哪儿
askdb/guard.py · sensitive_output_columns（约 1220 行）
省多少
本条至少 −1 轮补救决策；抽样 43 次拦截里 P03 占 2 次
质量方向
升。今天的行为是对合法查询的系统性误杀
怎么验
加一条三分支 UNION 的单测，断言返回 set 而非 None，且敏感列位置判对；扫审计里 rejected_by=P03 改后归零
C3

提示词从不告诉模型这是什么方言

提示词 · 确定性

askdb/agent.py 全文没有 dialect、PostgreSQL、MySQL 任何一个字样。模型在写 SQL 时不知道自己面对的是哪个方言，只能在执行时才发现。

抽样 63 条多步链路的 43 次拦截里，6 次（14%）是方言 / 语法错：

错误次数来源
DISTINCT is not implemented for window functions2DuckDB
(1064, "You have an error in your SQL syntax…")2MySQL
column "…" must appear in the GROUP BY clause2PostgreSQL（含本条第 11 步）

本条第 11 步就是这一类 —— SUM(COUNT(*)) FILTER (…) OVER () 在 PG 上非法。代价 11 ms 的拦截 + 3,103 ms 的补救决策。

修法：render_agent_system 里加一行「本次数据源方言：{dialect}，只写该方言合法的 SQL」。约 15 个 token，而且按源固定、不随请求变 —— 缓存条目数从 1 变成 2~3，不是每请求一份，前缀缓存的纪律不破。

质量方向
中性偏升。不放松任何护栏，只是让模型知道靶子在哪
怎么验

C4

每一次拦截都要付一整轮完整决策

结构 · 须影子标定

抽样 63 条多步链路、230 次工具调用，拦下 43 次（18.7%）。拦截之后那一轮补救决策均摊 4,772 ms，63 条合计 205 秒 —— 平均每条多步链路要为"写错 SQL"付 3.3 秒。

今天的补救路径是：拦截 → 结束这一轮 → 下一轮带着全量 schema + 全部 history 重新决策（约 6,000 输入 token、4.8 秒），而它实际要做的只是改一条 SQL。

  • 窄上下文修复调用。只带失败的 SQL、错误原文、guard 给的 hint、涉及表的 DDL —— 不带 history、不带全量 schema，输出只要一条 SQL。按 §03 的公式约 1,170 + 14.4 × 90 ≈ 2.5 s，对 4.77 s 省掉一半。
  • 这一轮不计入 max_steps。今天一次拦截扣掉六分之一的探索预算，等于用预算惩罚模型犯错，最后交一份证据不全的答案 —— 本条第 07 步就是这么把预算耗掉的。另设 max_repairs=2 防死循环，上界仍然确定。

这一条同时改了行为分布，按既定纪律必须 off / shadow / enforce 三档，先影子跑两轮标定。影子期要盯的是：修复后的 SQL 与被拦那条的 AST 表集合是否一致（防止窄上下文把意图改掉）、R-11 拦截率、接地校验 ungrounded 命中率。

真正的收益不在这张表里

−14.5% 不算大。这份方案值得做的理由是 C1： 29% 的多步链路今天交付的是一句"未在预算内完成归因"加一张裸表，而审计面板上它们全记 ok=true。 本条更极端 —— 一份写得很好的答案已经生成出来了，被一行 if finish: 丢掉。 这是质量缺陷，顺带才是延迟缺陷。

07

与 V1.4 的关系

docs/design-agent-trace-optimization.html（V1.4，依据 trace 4bac5ce7f21b）的六条改动已全部部署，本条链路上逐条确认生效： 工具轮没有 search_schema、没有 analyze_result、embedding 用量已进 span。 V1.4 在生产实测里已经指出过一句话 ——

「模型连撞三次护栏，把步数耗光。这跟这次的改动无关，但它说明一件对本方案不利的事： P0-2『一轮一条 SQL』在这种反复撞墙的链路上省不下什么 —— 步数是被失败重试吃掉的，不是被冗余核对吃掉的。」

本文是那句话的后续：第二例出现了，而且这次量化了它 —— 拦截率 18.7%、每次拦截 4,772 ms、29% 的多步链路因此跑满预算而交不出归因。 C2 / C3 削的是拦截发生率，C4 削的是每次拦截的单价，C1 兜的是已经发生之后不要把答案一起丢掉。三层各管一段，互不替代。
