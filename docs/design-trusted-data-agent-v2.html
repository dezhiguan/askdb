askdb · v2 架构提案

可信数据 Agent：让 LLM 自主决策，让 Runtime 强制安全

把 askdb 从「受控 NL2SQL 管道」重定位为「可信数据 Agent」。四层各司其职：Skill 给方法论、Tool 给原子能力、LLM 负责自主决策、Runtime 负责权限/安全闸/人工介入/Checkpoint/预算。安全性不靠限制自主，而靠把闸门钉在 Tool 边界。

拟制 2026-09-11版本 v2.0 草案承接 tech-design §2.1 / §1.2依据 线上实测 150 账号 / 1370 ask
核心命题不变，仍是「在模型不可靠的前提下让整条链路可靠」——变的只是可靠性的落点。自主性放在编排（LLM 选工具），可靠性钉在执行（每次 execute_sql 独立过闸），越界处人工介入（审批 / 复核），全程可中断可恢复（Checkpoint）。这些正交，所以「更自主」与「更可信」可以同时成立。

§1 端到端全景：从自然语言到返回结果

一次查询的完整走法，含四类此前没画全的机制：意图预检（接地判可答/越域/单步或多步）、复杂任务多步循环（决策→工具→执行→评估→回环）、人工介入（紫色：高成本/高风险动作挂起审批、结果人工复核）、中断恢复（左侧 Checkpoint 轨：任一挂起点持久化后可续跑）。

关于「第一步要不要大模型做意图识别」

要，但不是盲分类，是"接地(grounded)预检"。askdb 只有一个意图域（把 NL 变成对选定源的 SQL），没有多意图要路由；而且没看 schema 之前根本判不了"供应商在不在这个库"——盲分类会重犯实测那个攀附 bug。

有价值的是一个便宜的预检节点，把三件事合成一次调用：① 可答性 / 澄清（缺对象、纯指代）② 越域拒答（看过召回 schema 后判，省掉后面白跑一轮生成）③ 单步 / 多步初判。即把现有 clarify + plan 合并并接地，就是图中「意图 / 可答性预检」那一格。

本轮新补进流程的四类机制

复杂任务：中部循环带——决策→工具→执行→评估→不够则回环，受 R-16/R-17 封顶。人工介入：dry_run 超阈值/高风险动作挂起后人工审批；finalize 后高敏结论可选人工复核。中断恢复：左侧 Checkpoint 轨，任一挂起点（审批等待、复核等待、主动暂停）都先持久化，可续跑。意图预检：见上。

§2 长任务 → 自动异步：怎么判定短 / 长

别指望一次预判准。两层：Tier 1 预判（跑重活前的便宜信号，命中即立即异步）+ Tier 2 运行时兜底（同步跑超墙钟阈值就地提升为异步）。两条都落到同一处——写 checkpoint、建任务、前端提示「耗时较长，请到任务中心查看」、后台续跑。异步与「中断恢复」是同一套 checkpoint 机制，人工审批等待只是它的一个特例（等人＝无界时间，必然异步）。

§3 任务中心：任务状态机

异步任务的全生命周期。三个终态（完成 / 失败 / 取消）加两个人工挂起态（等审批 / 待复核）。每次状态迁移都落 checkpoint，所以崩溃可从最近状态恢复、活动态随时可取消。挂起态等的是人，时长无界——这正是它必须异步的原因。

排队 / 运行

前端：分析中…

  • 「排队中…」/「分析中 · 第 k 步」进度
  • 可「取消」
挂起 · 等审批

前端：等待放行

  • 发起人：「预估扫描 X 行，待管理员放行」
  • 审批人：批准 / 驳回（带说明）
待复核

前端：结果待复核

  • 结果先不采信；复核人：采信 / 打回
  • 打回带原因，回运行补查
完成 / 失败 / 取消

前端：终态

  • 完成：结果卡 + SQL + 可信信号
  • 失败：原因 + 可重试；取消：已取消

§4 四层架构（职责视图）

LLM 在中间跑「我下一步需要什么 → 选工具 → 看结果 → 还需要什么」的循环；三个原子工具环绕；Skill 从旁注入领域口径；整个循环被 Runtime 包住，安全闸就长在 execute_sql 这个原子内部——无论 LLM 怎么决定发的，都走同一条代码判定的闸。

§5 每层的职责 —— 与它绝不能做的事

Skill

领域方法论

  • 口径固化：JD 按 chunk_type、文档数按 COMPLETED
  • 拒答规则：库里没有的实体不许攀同名列
  • 软删除 / 指标归口 / 同义问法统一
✕ 不写死 SQL、不碰执行
Tool

原子能力

  • search_schema / get_table_schema / execute_sql
  • 每个都是自足、可独立审计的原子
  • execute_sql 自带安全闸（见下）
✕ 不做编排、不跨工具记忆
LLM

自主决策

  • 判断下一步需要哪个工具、查什么
  • 读 Tool Result 决定是否继续 / 收敛
  • 综合证据产出归因结论
✕ 不判断安全、不自证正确
Runtime

权限 / 安全 / 人工 / 边界

  • execute 强制过 guard→dry_run→只读→脱敏
  • 高成本/高风险 → 挂起人工审批；结果可人工复核
  • 预算封顶 R-16/R-17 · Checkpoint 可复现 · 全量审计
✕ 不信任 LLM 的任何安全判断

§6 三个承重条件（缺一个就不"可信"）

  1. Skill 层才是"可信"的来源，不是 loop。一个纯 ReAct loop 套这三个工具，会原样复现本轮实测查出的全部错误。把它们扳正的是 Skill 里的口径，不是更强的自主性。
    实测证据 · 更自主 ≠ 更对：「JD 文档数」agent 用 file_type 得 0（正确 chunk_type=15669）；「供应商」攀到 model_config.vendor 答 3（应拒答）；「简历数」软删除时过滤时不过滤（9 vs 62）。这三个错，多给自主只会多几种错法。
  2. 安全闸钉在 Tool 边界，不随自主性松动。沿用 §2.1 铁律「[4] 永远是代码判定」。LLM 决定发哪条 SQL，但每条都独立过 guard/dry_run/只读/脱敏——agent 无法用安全原子拼出不安全动作。
  3. Runtime 挡住 loop 新引入的风险。失控循环/成本爆炸 → 复用 R-16 步数上限 / R-17 累计成本上限 + 超时；多步累积泄露(§10.1) → 每个 Result 都过脱敏+租户、carry 只带标识列(R-15)；不可复现 → Checkpoint replay，把 run-to-run 变化的路径原样留档。

§7 这不是重写：原子已存在

三个工具在 askdb 里都已有实现——只是从固定管道里拆出来暴露成工具，再用 LLM loop 替掉那个"永远单步"的薄壳。mcp_server.py 已把 askdb 作为工具暴露给外层 agent，因此「loop 跑在 askdb 内」与「跑在外层 agent」收敛成同一件事：Tool 就是那条统一接口，跑在里还是外只是部署选择。

  • search_schema ← 现 schema_rag.py 向量召回
  • get_table_schema ← 现结构内省 / /api/schema
  • execute_sql ← 现 guard → dry_run → 只读执行 那条链，原样成为工具内部契约
  • 人工审批 ← 现 approval（P07 高成本挂起）；人工复核 ← 现 review（结果采信）；中断恢复 ← 现 checkpoint + as_task 续跑线程

§8 一个必须走的手续：重定位

这套等于把 askdb 的产品定位改了，要动 §1.1/§1.2 并出新版本号——是产品决定，不能当实现细节偷偷改。

§1.2 旧非目标（需撤/改）

  • 不做多轮对话上下文
  • 不追求覆盖任意复杂分析型查询

v2 新定位

  • 可信数据 Agent：LLM 自主编排、Runtime 强制安全
  • 覆盖多步探索型 / 结果驱动 / 归因分析，且全程可审计可复现
  • 核心命题不变：模型不可靠前提下链路可靠
