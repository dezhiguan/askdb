# askdb

**可信数据问答 Agent —— 把自然语言转换为受控 SQL 并安全执行。**

核心命题不是"让模型会写 SQL"，而是**在模型不可靠的前提下，让整条执行链路可靠**。

---

## 它和通用 Agent 的区别

给一个通用 Agent（Claude Code、Cursor，或任何带 `run_sql` 工具的 ReAct agent）一个数据库连接，它也能回答这些问题，而且更灵活 —— 探索能力更强、长尾覆盖更广、不需要预先配置。

**askdb 不追求更聪明，追求可以被信任地重复执行。**

| | 通用 Agent | askdb |
|---|---|---|
| 灵活性 / 探索 / 长尾覆盖 | **胜** | 受限于表白名单 |
| 约束强度 | 软约束（提示词层面） | **硬约束（AST 改写 + 数据库权限）** |
| 可测量性 | 每次行为不同，无法回归 | **链路固定，可回放、可消融** |
| 成本 | 探索式，事先不可预测 | **有界，可封顶** |
| 结构化审计 | 散落在对话里 | **每次调用一条 JSON 记录** |

一句话：**通用 Agent 是探针，askdb 是产线。**

| 场景 | 建议 |
|---|---|
| 自己临时查个数、探索不熟悉的库 | 用通用 Agent，askdb 打不过 |
| 高频重复调用 / 给不写 SQL 的人用 / 要保证不跨租户 / 要能说出准确率 / 要留审计 | 用 askdb |

## 执行链路

```
用户问题
   │
   ├─▶ [1] Schema 召回      仅注入命中的表与业务口径，不做全库注入
   ├─▶ [2] 规划 / 重规划    判定单步可答或需多步
   ├─▶ [3] SQL 生成         结构化输出，强制 JSON schema
   ├─▶ [4] 静态校验         AST 判定 + 强制改写 · 零 token 成本
   │        └── 不通过 ──▶ [7] 反思重试 ──▶ 回到 [3]（次数受限）
   ├─▶ [5] EXPLAIN 干跑     预估扫描行数，超阈值打回
   ├─▶ [6] 只读执行         独立只读账号 + 超时 + 行数上限
   ├─▶ [8] 结果评估         本步是否足以作答？不足则回到 [2]
   └─▶ [9] 结果与溯源       结果 + 全部轮次 SQL + 数据时间
```

**设计原则：第 4 步永远是代码判定，不是模型判定。** 让模型审查自己的产出等同于没有护栏。

## 护栏规则

| 编号 | 规则 | 类型 | 状态 |
|---|---|---|---|
| R-01 | 单语句限制（防多语句夹带） | 静态校验 | ✅ |
| R-02 | 语句类型白名单（仅 SELECT / WITH…SELECT） | 静态校验 | ✅ |
| R-03 | 表白名单（含子查询、CTE、JOIN 中的全部引用） | 静态校验 | ✅ |
| R-04 | 字段真实性（拦截幻觉字段） | 静态校验 | ✅ 部分¹ |
| R-05 | 禁止 `SELECT *` | 静态校验 | ✅ |
| R-06 | 禁止跨 schema / 跨库引用 | 静态校验 | ✅ |
| R-07 | 危险函数黑名单 | 静态校验 | ✅ |
| R-08 | 笛卡尔积检测 | 静态校验 | ✅ |
| R-09 | **强制 LIMIT 注入** | 强制改写 | ✅ |
| R-10 | **强制租户谓词注入** | 强制改写 | ✅ |
| R-11 | 扫描行数阈值（EXPLAIN） | 干跑 | ✅ |
| R-12 | 语句超时 | 执行限制 | ✅ |
| R-13 | 结果行上限 | 执行限制 | ✅ |
| R-14 | 重试次数上限 | 链路控制 | ✅ |
| R-15 | 中间结果规模上限（多步） | 链路控制 | ✅ |
| R-16 | 总步数上限（多步） | 链路控制 | ✅ |
| R-17 | 累计成本上限 | 链路控制 | ✅ |

¹ 已覆盖带表限定的字段、以及作用域内只有一张表时的裸字段；多表 JOIN 下的裸字段解析待补。

**强制改写在 AST 上完成后重新生成 SQL，模型无法通过任何提示词手段覆盖：**

```sql
-- 模型产出
SELECT file_name, status FROM documents WHERE status = 'PROCESSING';

-- 实际执行
SELECT file_name, status FROM documents
WHERE status = 'PROCESSING'
  AND documents.org_id = 65   -- R-10 强制注入
LIMIT 1000;                   -- R-09 强制注入
```

多租户隔离采用双层：**应用层 AST 改写**（R-10）+ **数据库行级安全 RLS**（PostgreSQL）。
仅靠应用层改写不足以保证隔离 —— 子查询、CTE、UNION、视图任一分支遗漏即构成越权路径。

## 快速开始

```bash
git clone https://github.com/dezhiguan/askdb.git && cd askdb

# 依赖 Python >= 3.10；推荐用 uv
uv venv --python 3.12 && uv pip install -e .

# 生成本机样例库（固定随机种子，任何人生成的数据完全一致）
python -m data.seed

# 配置模型密钥
cp .env.example .env   # 填入 DASHSCOPE_API_KEY
```

不接入任何外部数据源即可运行 —— 样例库自带文档、知识库、组织、token 计量四张表。

```bash
askdb check                              # 配置与数据源自检，先跑这个
askdb sql "SELECT file_name FROM documents WHERE status='PROCESSING'"
askdb ask  "有哪些文档卡在处理中超过一小时"
askdb serve                              # Web 界面 http://127.0.0.1:8000
```

**`askdb sql` 不需要模型密钥** —— 跳过生成，直接跑 护栏 → 干跑 → 执行，
在配置任何东西之前就能把整条护栏链路验证一遍。

## 配置

三份 YAML，职责分离：

| 文件 | 内容 |
|---|---|
| `config/askdb.yaml` | 数据源、租户策略、护栏阈值、模型 |
| `config/tables.yaml` | **表白名单与字段语义注释** |
| `config/metrics.yaml` | **业务口径定义** |

后两份是准确率的决定因素，而不是提示词调优：

```yaml
# tables.yaml —— 字段名不具自解释性，必须补业务语义
status:
  desc: "处理状态。注意：「文档数」口径为 COMPLETED 的数量，不是全部行数"
  enum: [PENDING, PROCESSING, COMPLETED, FAILED]
org_id:
  desc: 组织 ID
  tenant: true        # ← 标记租户列，触发 R-10 强制改写
```

```yaml
# metrics.yaml —— 模型永远猜不出来的那一层
- name: 卡住的文档
  aliases: [卡住, 处理中不动, 堆积的文档]
  predicate: "status = 'PROCESSING' AND updated_at < now() - INTERVAL 1 HOUR"
```

## 实测结果

两套评测，跑在**两个不同的库**上。放在一起是因为对比本身就是结论。

| | 合成样例库 | **真实生产库** |
|---|---|---|
| 数据 | `data/seed.py` 固定种子生成，10.4 万行 | ragforge（org 316），13 959 文档 / 1 407 检索日志 |
| 表名与注释 | 规范、齐全 | 真实业务命名，注释靠 `tables.yaml` 补 |
| 租户列 | 每张表都有 | `documents` **没有**，要经 `kb_id` 绕子查询 |
| 缓存计数器 | 无 | `doc_count` **实测已漂移**（缓存 12 274 / 实际 12 280） |
| 题库 | `evals/golden.jsonl` | `evals/golden-ragforge.jsonl`（冻结标签 `golden-ragforge-v1`） |
| 盲测准确率 | 50.0% | **62.5%** |

设计文档 §1.2 判定"真实企业库的准确率落在 40–60%，与学术基准不可比"。
合成库正是它说的那种理想环境 —— 所以**只看合成库那组数字没有意义**，
本节以生产库那组为准。

### 一、真实生产库（推荐以此为准）

**ragforge @ org 316 · deepseek-v4-flash · 2026-08-12 · 全部实跑**

#### 盲测集 —— 最终成绩

17 题，全程不参与调参，可作答 16 道。

| 指标 | 值 |
|---|---|
| **执行准确率** | **62.5%** |
| 误拒率 | 6.2% |
| 应拒拦截率 | 100% |
| 多步误用率 | 0% |
| P95 延迟 | 7.7 s |
| 总成本 | ¥0.0588 |

失败分类（不做筛选）：结果不一致 4 · 链路失败 1 · 被护栏拦截 1。
每条带 `trace_id`，`askdb replay <trace_id>` 可原样复现判定链路。

> **盲测集实际运行了三次，三次结果全部公开。** 前两次是 56.2%，第三次
> 62.5%。差异来自判定器的一处缺陷：被判定的答案经 `jsonable()` 已是字符串，
> 标准答案是 `Decimal`，类型不同导致数值容差分支进不去 —— 模型写 `AVG(x)`
> 而标准写 `ROUND(AVG(x),1)` 被判为错，日均成本那题模型 SQL 与标准**逻辑
> 完全一致**也被判错。
> **这个修复是在看到盲测结果之后做的，且抬高了成绩** —— 这正是 §6.4 要防
> 的那类操作。修复前的结果原样留档为 `ragforge-blind-run1-buggy-comparator.json`，
> 未删未改。容差取 1e-4 且不是照题调的（需抹平的舍入差 2e-5，需保留的口径
> 错 55%）。污染风险客观存在，此处标明。

#### 消融实验（非盲测 41 题，可作答 37 道）

| 组 | 配置 | 准确率 | 增量 | 95% 置信区间 | 误拒率 | 成本 | P95 |
|---|---|---|---|---|---|---|---|
| A | 裸 Prompt（全量 schema，无护栏改写/重试/口径） | 48.6% | — | [33.4%, 64.1%] | 2.7% | ¥0.085 | 2.2 s |
| B | + Schema 召回 | 51.3% | +2.7pp | [35.9%, 66.6%] | 2.7% | ¥0.064 | 2.3 s |
| C | + 静态校验重试 | 48.6% | −2.7pp | [33.4%, 64.1%] | 2.7% | ¥0.068 | 2.6 s |
| **D** | **+ 语义层口径** | **62.2%** | **+13.5pp** | [46.1%, 75.9%] | **0.0%** | ¥0.066 | 1.9 s |
| E | + 干跑阈值（单步全链路） | 62.2% | +0.0pp | [46.1%, 75.9%] | 0.0% | ¥0.066 | 2.0 s |
| F | + 多步规划 | 59.5% | −2.7pp | [43.5%, 73.7%] | 0.0% | ¥0.139 | 4.3 s |

按题型拆开后，D 的增量来自哪里一目了然：

| 组 | 单表 | 多表关联 | **口径依赖** | 时间窗口 | 多跳 |
|---|---|---|---|---|---|
| A | 10/10 | 1/10 | **0/7** | 2/4 | 5/6 |
| C | 9/10 | 1/10 | **0/7** | 4/4 | 4/6 |
| **D** | 9/10 | 2/10 | **3/7** | 3/4 | 6/6 |
| E | 9/10 | 2/10 | 3/7 | 3/4 | 6/6 |

**没有口径定义，模型在口径题上 0/7 —— 一道都答不对。** 这是整份消融里唯一
指向明确的结论，而它在合成库上完全测不出来：那里六个口径有三个退化
（无 PENDING 文档、`parent_document_id` 全 NULL、检索日志 100% SUCCESS），
用不用口径结果一样。

**多步规划仍按预设规则默认关闭。** F 组多跳准确率 **100% → 100%**、成本
**+110%**，且平均步数始终为 1.0（规划器从未真正触发多步，多花的钱全在
plan/assess 两次额外模型调用上）。判据是消融脚本里预先写死的，不是事后定的。

### 二、必须说明的四点（都对本项目不利）

1. **没有一项差异在统计上显著。** 相邻组配对检验（McNemar 精确，同题）：

   | 对比 | 变好 | 变坏 | p 值 |
   |---|---|---|---|
   | A→B | 4 | 3 | 1.000 |
   | B→C | 0 | 1 | 1.000 |
   | **C→D** | **6** | **1** | **0.125** |
   | D→E | 0 | 0 | 1.000 |
   | E→F | 1 | 3 | 0.625 |

   即便是最大的 C→D（+13.5pp）也不显著。n=37 时**答对 1 题 = 2.7pp**，
   低于约 8pp 的差异读不出意义。要得到显著结论，题量需要上一个数量级。

2. **多表关联只有 1–2/10，而这主要是我的题目不够精确，不是模型不会写 JOIN。**
   复现失败样本后看到三类：模型多返回一列 `kb.id`（语义答对，判定按精确列集
   比对判错）；`LEFT JOIN` vs `JOIN`（空知识库算不算，题面没说）；分组维度
   两可（"各知识库用什么向量模型"可读作按库列出，也可读作按模型分组）。
   设计文档 §6.2 只规定"列顺序无关"，**没界定多返回一列算不算对**。
   **黄金集已冻结，不改** —— 改判定器让自己分数变高，正是 §6.4 要防的操作。
   记录在此，留给 v2 修订题面。

3. **口径层的增益有我自己的选择在里面。** 生产库上原六个口径三个退化，
   我据实测分布补入了六个**有区分度**的口径 —— 即"按定义算"与"凭直觉算"
   结果不同的那些。这是语义层本该做的事，但也意味着 D 组的增量部分来自
   "题目就是冲着口径出的"。退化口径一律未用于出题，理由与实测分布都写在
   `config/ragforge-prod-metrics.yaml` 里。

4. **同一配置两次跑结果不同。** `temperature: 0` 不保证确定性 —— 盲测第二、
   三次误拒率从 0% 变为 6.2%。所有单次数字都应视作带噪声的观测。

### 三、合成样例库（保留对照）

**10.4 万行 · deepseek-v4-flash · 2026-08-12**

盲测 18 题：准确率 **50.0%** · 误拒 6.2% · P95 22.9 s · ¥0.0599。

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 编排 | `langgraph` | 需要条件路由与状态持久化 |
| 抽象 / 模型 | `langchain-core`、`langchain-openai` | 结构化输出；OpenAI 兼容端点 |
| **SQL 解析与改写** | `sqlglot` | AST 可改写，是强制注入的前提 |
| 数据 | DuckDB（内置样例）/ PostgreSQL | |
| 对外 | FastAPI + MCP | MCP 按 2026-07-28 无状态规范 |

**不使用 `langchain` 主包**：`AgentExecutor` 不支持条件路由与状态持久化，失败无法从中间节点续跑，而这三项是本设计的必要条件。

## 生产使用边界

| 场景 | 结论 |
|---|---|
| 连接生产**主库** | **禁止** —— 无人值守的聚合查询有拖垮主库的现实风险 |
| 连接**只读副本**，限具备 SQL 阅读能力的人员使用 | 有条件允许（需满足只读账号 + RLS + 审计 + 配额等 8 项准入条件） |
| 面向**终端用户**开放 | **禁止** —— 终端用户无法核对 SQL，错误口径将直接进入决策 |

**关于"可信"的定义**：只要底层由 LLM 生成 SQL，就不存在"结果一定正确"。
本项目所称可信指**过程可信**（危险操作可被拦截、结果可被自验、判定链路可被追溯），
而非**结果可信**。输出必须附带 SQL 供人工核对。
